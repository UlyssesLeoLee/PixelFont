## 1. 范围与目的

### 1.1 为什么还要审

文档写完不等于文档对。规格文档的风险不在「写得不好看」，而在**它看起来对**：
一条命令写错一个系数、一个文件名叫错一个字、一处哈希抄错一位，
在 Markdown 里全都语法合法、读起来全都合理。

所以这一轮不审「表述是否优美」，只审**每一条断言能不能被机器证伪**。

### 1.2 三轮的攻击面

沿用仓库既有的方法论（[`docs/adversarial-review.md`](../adversarial-review.md) 是
字形层的三轮审核，本报告是**文档层**的三轮审核，攻击面互相独立）：

| 轮 | 攻击面 | 一句话 | 工具 |
|---|---|---|---|
| R1 | 身份反查 | 不看文档说了什么，直接问仓库「有没有这个东西」 | `tools/specreview/audit_identity.py` |
| R2 | 部件级结构 | 看结构能不能立住：表格列数 / 章节引用 / 链接 / 本机路径 | `tools/specreview/audit_structure.py` |
| R3 | 链条 | 把各文档第 4 节的复现命令**真跑一遍** | `tools/specreview/audit_chain.py` |
| 附 | 事实核验 | 每个 sha256 / 码位是否在白名单里，跨文档数字是否自洽 | `tools/specreview/verify_facts.py` |

### 1.3 不在范围内

- 不审文档的**技术选型**对不对（例如方案 C 是不是最优解）——那是另一个问题；
- 不审**多语言版实现**（Multi 12 尚未开工，没有实现可审）；
- 不重跑字形层三轮审核（那一轮已由 `tools/fontgen/adversarial_review.py` 覆盖）。

### 2.2 审核工具自己翻了 10 次车 —— 记录在案

这一节是本报告最有价值的部分。**审核工具的假阴性比文档缺陷更危险**：
一份说「0 条问题」的报告，如果量具本身坏了，那 0 条就毫无意义。

| # | 工具的 bug | 后果 | 修法 |
|---|---|---|---|
| T1 | `git cat-file -e` 成功时**没有任何输出**，脚本按「stdout 为空」判「commit 不存在」 | 全部 commit 引用被判为不存在 | 改看**返回码** |
| T2 | R3 v1 把 PowerShell 块里的 `python -c "..."` 当 Python 块跑 | 误判失败 | 按围栏语言分派 |
| T3 | bash 块先写文件再执行，Windows 路径把脚本吃掉 | 误判失败 | 改用 `bash -c` 直接喂脚本 |
| T4 | ```` ```python ```` 围栏被当成 PowerShell | 误判失败 | 围栏语言严格分派 |
| T5 | 纯「期望输出」块（只有输出、没有命令）被当成命令执行 | 误判失败 | 增加「是否含命令」判定，输出块记 OUT |
| T6 | 表格列数统计**没有排除已转义的 `\|`** | 误报「列数不一致」 | 列数只数未转义竖线 |
| T7 | R2 把字符串当元组索引（`ctx[0]` 取到的是**首字符**而不是首元素） | 判据跑偏 | 显式转 tuple 或改用 split |
| T8 | 核验器指向**已回收的 worktree**（`E:\PixelFont-lanes\wt-spec12-*`） | 12 份文档全报 MISSING —— 假阴性「文档不存在」 | 路径改为仓库内 `docs/spec/`，并从 `__file__` 推导仓库根 |
| T9 | 事实底稿入仓后，一致性核验的分母从 12 变成 13，超过区间上限 | 4 项**假失败** | 核验器区分「12 份规格文档」与「支撑文档」两个集合；底稿改用「必须 100% 覆盖」判据 |
| T10 | R1 用**文件系统存在性**判定 `dist/` 下的路径 | 干净 clone 上必然误报（`dist/` 按政策不入库） | 改用 `git ls-files` 判**入库性**；`dist/` `third_party/` 按政策标记为「不入库」 |

**判别式**：任何「审核通过」的结论，都必须先证明审核器本身没坏。
本仓库的做法是**正反对照**（注入已知缺陷必须被抓到）+ **白名单**（未知哈希/码位一律判失败）。

## 4. 复现命令

```bash
# 在仓库根目录执行, 四个脚本互相独立, 可单独运行
python tools/specreview/audit_identity.py    # R1 身份反查
python tools/specreview/audit_structure.py   # R2 部件级结构
python tools/specreview/audit_chain.py       # R3 链条复跑 (耗时约 1 分钟)
python tools/specreview/verify_facts.py      # 事实核验 + 跨文档一致性

# 索引同步 (只检查不写入: 加 --check)
python tools/specreview/sync_index.py
```

说明：

- 四个脚本都从 `__file__` 推导仓库根，**在任意机器的任意检出路径下都能跑**；
- R3 需要 `dist/` 下有构建产物（发布包），没有时相关块会失败并明确报缺哪个文件；
- R3 的临时目录在系统临时目录下（`pf_specreview_chain/`），不污染仓库。

## 5. 已知边界与待办

1. **R3 的覆盖是「命令能跑」，不是「输出与文档声称一致」**。
   当前判据是「退出码 0 且输出里没有错误特征」；文档正文里写的期望输出**没有逐字比对**。
   要做逐字比对需要把期望输出结构化成机器可读的断言，属于后续工作。
2. **R1 的 API 存在性是文本级的**（在源码里找 `def xxx(`），不做 AST 解析，
   因此对动态生成的方法会漏判。当前 12 份文档里没有依赖动态 API 的引用。
3. **一致性区间（22 项）是人定的**，不是从事实推导出来的。
   区间过宽等于没查（例如「UPM 768」只要 6 份文档提到就算通过）。
   更严格的做法是每个关键数字在**所有相关文档**里都必须出现且取值唯一。
4. **本轮只审了文档层**。文档里的**技术判断**是否成立（例如方案 C 优于方案 A/B）
   属于设计评审，不在本轮攻击面内。
5. Multi 12 实现开工后，需要对**新代码**再走一轮对抗式审核；
   本轮的工具链可以直接复用，但要补一条「构建产物与文档声称的字符集逐位一致」的判据。
