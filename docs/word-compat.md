# Word / Windows 兼容性

## 结论（先行）

**字体内容没有问题，问题全在字体的 OS/2 元数据里。**

旧版 TTF 的 4140 个字形轮廓逐像素校验通过，但它的 `OS/2` 声明写错了三处，
后果是 Windows 的字体映射器**根本不会选中这个字体**：

| Word 的字体请求 | 修复前实际选中 | 修复后 |
|---|---|---|
| 西文（ANSI charset） | **Arial** | PixelFont PC98 12 |
| 简体中文（GB2312 charset） | **宋体** | PixelFont PC98 12 |
| 日文（Shift-JIS charset） | PixelFont PC98 12 | PixelFont PC98 12 |
| 韩文 / 繁体（字体不含这些字形） | Ebrima | Ebrima（**选不中才对**） |

这就是"字体明明装了，Word 里却像没装"的直接原因：中文正文被系统换成了宋体，
西文被换成了 Arial，只有日文假名命中了本字体。

除此之外还有**两条使用侧的硬约束**（不是文件的缺陷，改文件也解决不了）：
字号必须取 **12 的整数倍**（Word 中文默认的 10.5pt 不满足），
以及字体还**缺 21 个常用字符**（含中文弯引号「“ ”」和全角空格 U+3000）。

> **当前状态（2026-10-24）**：这两条使用侧约束**已经处理完**——
> 字符集补到 4161，字号问题见第 9 节（取 12 的整数倍即可）。
> 本机已安装的那份仍是 2026-10-23 的旧版，**必须覆盖安装**新文件才能生效，
> 步骤见 [`docs/install.md`](install.md)。
> 本文所有数字都能由第 8 节的命令复现。

## 1. 根因一：`ulCodePageRange1` 声明的代码页完全错了

### 1.1 位号对照（OpenType OS/2 规范 1.9.1）

`ulCodePageRange1` 的位号不是"东欧/俄文"那一套，规范里的表是：

| 位 | 代码页 | 含义 |
|---|---|---|
| 0 | 1252 | Latin 1（**ANSI**，即西文） |
| 16 | 874 | 泰语 |
| **17** | **932** | **日文 JIS** |
| **18** | **936** | **简体中文** |
| 19 | 949 | 韩文 |
| 20 | 950 | 繁体中文 |

旧代码写的是：

```python
ulCodePageRange1=(1 << 16) | (1 << 17),  # 日文(932) + 简体中文(936)   ← 注释与实现不符
```

实际值 `0x00030000` = bit16 + bit17 = **874 泰语 + 932 日文**。

- 注释说"日文 + 简体中文"，但 936 的位号是 **18**，写进去的是 **16（泰语）**——字体里一个泰文字形都没有，这是**虚报**。
- 真正需要的 **1252（bit0）** 和 **936（bit18）** 两位**都没写**。

### 1.2 后果的实证（GDI A/B）

`tools/fontgen/verify_gdi.py` 用的是 Word 背后的同一条路径：把字体注册进 GDI，
然后用 `CreateFontIndirectW` 按各种 `lfCharSet` 请求它，看 GDI 到底把谁给了我们。

同一个字体文件，只改 OS/2 两位，结果：

```
== 修复前 ==
  [SUB] lfCharSet=  0 ANSI      选中='Arial'      ← 西文不吃本字体
  [SUB] lfCharSet=134 GB2312    选中='宋体'        ← 中文不吃本字体
  [OK ] lfCharSet=128 SHIFTJIS  选中='PixelFont PC98 12'

== 修复后 ==
  [OK ] lfCharSet=  0 ANSI      选中='PixelFont PC98 12'
  [OK ] lfCharSet=134 GB2312    选中='PixelFont PC98 12'
  [OK ] lfCharSet=128 SHIFTJIS  选中='PixelFont PC98 12'
```

修复后的值：

```python
ulCodePageRange1=(1 << 0) | (1 << 17) | (1 << 18),  # 1252 + 932 + 936
```

与 Windows 自带的中文字体一致（SimSun 是 `0x00040001` = 1252 + 936）。

### 1.3 连带修掉的虚报

`ulCodePageRange2` 保持 0（字体不含任何 OEM 代码页字符），
并在 `verify_ttf_metadata()` 里加了断言：声明了泰语位或 range2 非零就**拒绝构建**。

## 2. 根因二：`fsSelection` 缺 REGULAR 位

旧值 `0x0000`。Windows 自带字体全是 `0x0040`（bit6 = REGULAR）：

| 字体 | fsSelection |
|---|---|
| SimSun | 0x0040 |
| MS Gothic | 0x0040 |
| Arial | 0x0040 |
| Segoe UI | 0x0040 |
| **本字体（修复前）** | **0x0000** |
| 本字体（修复后） | 0x0040 |

缺 REGULAR 位时，Word 不会把它当成一个"常规体"来呈现（样式面板 / 字体列表里
可能出现异常的显示名，也影响部分应用的字体族归并）。已在构建期设为 `0x0040`，
并加了断言：必须带 REGULAR、不得带 ITALIC。

---

## 3. 根因三：`ulUnicodeRange` 既虚报又漏报

旧值手写为 `ulUnicodeRange1 = 0x6000000F`（bit 0,1,2,3,29,30）。按规范核对：

| 位 | 块名 | 旧声明 | 字体里实际有没有 |
|---|---|---|---|
| 0 | Basic Latin | ✅ | 有 |
| 1 | Latin-1 Supplement | ✅ | 有（× ÷ ·） |
| 2 | Latin Extended-A | ❌ **虚报** | 没有 |
| 3 | Latin Extended-B | ❌ **虚报** | 没有 |
| 29 | Latin Extended Additional/C/D | ❌ **虚报** | 没有 |
| 30 | Greek Extended | ❌ **虚报** | 没有 |
| 31 | General Punctuation | ⚠️ **漏报** | 有（— …） |
| 48 | CJK Symbols and Punctuation | ⚠️ **漏报** | 有（、。《》「」『』【】） |
| 49 | Hiragana | ⚠️ **漏报** | 有 |
| 50 | Katakana | ⚠️ **漏报** | 有 |
| **59** | **CJK Unified Ideographs** | ⚠️ **漏报** | **有（3755 个 GB2312 一级汉字）** |
| 68 | Halfwidth and Fullwidth Forms | ⚠️ **漏报** | 有（￥ 等） |

两个方向都会出事：

- **虚报**：系统认为本字体能画希腊文/西里尔文/拉丁扩展，于是在这些文本上把本字体
  当候选，命中后渲染成豆腐块（`.notdef` 空心框）。
- **漏报**：尤其漏掉 bit59（CJK Unified Ideographs）—— 系统据此判断"这不是中文字体"，
  在需要中文字形时直接跳过本字体去做回退。这与第 1 节观察到的"GB2312 请求下换成宋体"
  是同一件事的两个侧面。

**修复方式不是手写一张位表，而是交给 fontTools 按 cmap 实际覆盖重算**
（`O_S_2f_2.recalcUnicodeRanges`，数据来自 OpenType 规范 v1.7 的区段表）。
构建脚本里删掉手写的 `ulUnicodeRange1=...`，并加断言：
**声明的位集合必须与 cmap 实际覆盖算出来的位集合完全一致**（多一位少一位都拒绝构建）。

## 4. 根因四：字号必须是 12 的整数倍（使用侧约束，改文件解决不了）

本字体是 **12×13 网格**（em = 12px，`unitsPerEm = 768`，1 像素 = 64 单位）。
在 `ppem = 12k` 时，缩放比是整数，轮廓每个像素正好落在整数设备像素上；
在其它 ppem 上，12 的缩放比是无理数，**任何渲染器都不可能还原出原像素**。

GDI 实测（'中'，设计墨迹 37 格）：

| ppem | 缩放 | 墨迹格数 | 与设计位图一致 | 抗锯齿像素 |
|---|---|---|---|---|
| 12 | 1.00× | 37 | ✅ | 0 |
| 14 | 1.17× | 41 | ❌ | 0 |
| 15 | 1.25× | 43 | ❌ | 0 |
| 16 | 1.33× | 68 | ❌ | 0 |
| 18 | 1.50× | 47 | ❌ | 0 |
| 21 | 1.75× | 101 | ❌ | 0 |
| 24 | 2.00× | 148 | ✅ | 0 |
| 36 | 3.00× | 333 | ✅ | 0 |

14ppem 正是 **Word 中文默认字号 10.5pt @96dpi**。这一档没有"调参"的空间——
非整数倍缩放就是还原不出原像素。

### 4.1 该用哪些字号

`ppem = 字号(pt) × DPI / 72`，要求 `ppem % 12 == 0`：

| 显示缩放 | 有效 DPI | 1pt = | 像素精确的字号 |
|---|---|---|---|
| 100% | 96 | 4/3 px | **9 / 18 / 27 / 36 pt** |
| 125% | 120 | 5/3 px | 36 / 72 pt |
| 150% | 144 | 2 px | 6 / 12 / 18 / 24 / 30 / 36 pt |
| 200% | 192 | 8/3 px | **9 / 18 / 27 / 36 pt** |

在 100% 缩放下，**9pt（小五）= 12px、18pt = 24px、27pt = 36px、36pt = 48px**
都是 1:1 或整数倍——这四档在 Word 里就是像素字，其余字号是缩放结果。

> Word 的字号框可以直接输入数值，不必从下拉列表里挑中文标准字号。

## 5. 根因五：缺 21 个常用字符（**已修**，字符集 4140 → 4161）

对 48 个 Word 常见字符做的覆盖探针结果：**有 27 个，缺 21 个**。

缺的最要紧的是这三个：

| 码位 | 字符 | 为什么 Word 里绕不开 |
|---|---|---|
| U+201C / U+201D | “ ” | 中文输入法直接输出弯引号；Word 的自动更正也会把直引号 `'` `"` 转成弯引号 |
| U+3000 | 　（全角空格） | 中文排版的段落缩进、首行缩进就是它 |
| U+2022 | • | 手工项目符号 |

其余缺失：U+00A0（不换行空格）、U+00A5（¥）、U+00B0（°）、U+00BD（½）、
U+2013（–）、U+2018/2019（‘ ’）、U+2027（‧）、U+20AC（€）、U+2192（→）、
U+2260/2264/2265（≠ ≤ ≥）、U+FF3B/FF3D（［］）、U+FF5B/FF5D（｛｝）。

这些字形缺失时，Word 会**用别的字体补**（回退），表现是"像素字里夹着几个宋体字"。

### 5.1 补齐结果（2026-10-24）

21 个字形全部补入，字符总数 **4140 → 4161**（ASCII 95 + 标点 56 + 假名 255 + 汉字 3755）。

- **逐个在 12px 下目视确认**：弯引号、箭头、数学符号、全角括号都是规整点阵，
  无粘连、无裁切；零墨迹字形（U+00A0、U+3000）走 BDF 写入器已有的 `BBX 0 0 0 0` 分支。
- **来源**：弯引号 / 箭头 / 数学符号等走 MS Gothic，全角括号走 SimHei，全角空格走 MS Gothic。
- **生产源重新裁剪**：Fusion Pixel 裁剪版按新字符集重切（4157 个字形，裁剪前后逐像素一致）；
  Fusion 缺的 4 个（€ ≠ ≤ ≥）走 MS Gothic / SimHei，不走第三个源。

### 5.2 补齐顺带抓出一个**真缺陷**：U+005C 反斜杠画成了 ¥

补入 U+00A5（日元）之后，对抗审核的"我方近重复"检测报出：我方 U+005C 与 U+00A5
**整格逐字节完全相同**（两者整格 sha256 都是 `d647537c5cbf50a9`）。

把位图打出来才看清：MS Gothic 按 **JIS 惯例**把 U+005C 画成了 ¥
（日文键盘的反斜杠键位就是 ¥）：

```
U+005C 旧（错）      U+005C 新（对）
  #...#.              #.....
  #...#.              #.....
  .#.#..              .#....
  .#.#..              ..#...
  #####.              ..#...
  ..#...              ...#..
  #####.              ...#..
  ..#...              ....#.
  ..#...              ....#.
```

这个缺陷**一直存在**（ASCII 反斜杠一直在画 ¥），只是之前没有第二个 ¥ 形状的码位，
所以没人比对出来。对面向中文用户的字体这是硬伤：写文件路径、正则的人会看到 ¥。

**修法**：新增一条**非汉字码位的源例外**（`charset.SOURCE_OVERRIDES`）——
`ideo_route.json` 只覆盖汉字，而这是 ASCII 码位带着源字体语系惯例的问题，
必须单独切源。切到 Fusion Pixel（也是 12px 点阵，实测它的 `/` 与 MS Gothic 的 `/`
几乎同形：1px 斜线、起止行一致），画风上最贴。

## 6. 使用侧约束：Windows 的"字体平滑"

Windows 可以在系统层给所有文字加抗锯齿/ClearType（设置 → 系统 → 显示 → 高级显示 →
颜色管理 → 更改字体平滑设置）。本机实测该开关处于**开启**状态。

- Word 没有"按字体关闭抗锯齿"的开关（`gasp` 表是给渲染器的建议，Word 自己不一定照做）。
- 想要整个屏幕上的字都是硬边像素，只能在系统层把字体平滑设为"无"。
- 这一条**与字体文件无关**，是系统设置；本仓库不为此改字体。

补充说明（实测）：在本机的 GDI 内存 DC 上，即使系统平滑开着，
本字体渲染出来的**抗锯齿像素恒为 0**（12/14/24/36ppem 全部实测）。
所以在 Word 里"糊"的观感更可能来自**非整数倍字号**（第 4 节）而不是抗锯齿。

## 7. 已落地的修复与门禁

### 7.1 `tools/fontgen/build_font.py`

| 位置 | 改动 |
|---|---|
| `setupOS2()` | `ulCodePageRange1` → `(1<<0)\|(1<<17)\|(1<<18)`（1252+932+936） |
| `setupOS2()` | 新增 `fsSelection=0x0040`（REGULAR） |
| `setupOS2()` | 删除手写的 `ulUnicodeRange1=...`，改由 fontTools 按 cmap 重算 |
| `gasp` 表 | 从 `{12:0, 0xFFFF:GRIDFIT\|DOGRAY}` 改为 `{0xFFFF:0}`——**全字号单色、不做网格拟合** |
| `verify_ttf_metadata()`（新增） | 代码页位 / fsSelection / Unicode 区段位 / gasp 四组不变量，任一不符即拒绝构建 |

`gasp` 为什么改成全 0：像素字在任何字号都不该请求"灰度抗锯齿"（会糊），
也不该请求"网格拟合"（会让栅格化器的 autohinter 把 1px 竖画吸附撑粗）。
本机 GDI 实测新旧 `gasp` 在 12/14/15/16/18/21/24/36ppem 上**渲染结果完全相同**
（都是纯单色）——所以这一改动在 GDI 上不可观测，它的作用是**让声明与像素字的设计
意图一致**，并覆盖会照做 `gasp` 的渲染器。这一点不夸大。

### 7.2 `tools/fontgen/verify_gdi.py`（新增门禁）

直接问操作系统三件事：

1. **字体选择**：各 charset 请求下 GDI 选中了谁。覆盖到的必须选中；
   **没覆盖到的（韩文/繁体）必须选不中**——选中反而说明 OS/2 在虚报。
2. **字体枚举**：`EnumFontFamiliesExW` 在 ANSI/GB2312 下能否枚举到本族。
3. **栅格化比对**：用 GDI 把**每一个字**画进 24bpp DIB，拿墨迹与设计位图（BDF）逐格比对，
   同时统计抗锯齿像素。**不抽样**——抽 6 个字样只能证明那 6 个字没问题，
   而"这个字在 Word 里画对了吗"本来就是逐字的问题。

当前结果（`reports/gdi_compat.json`，全量扫 4161 个码位，耗时 9 秒）：

```
12ppem 墨迹外框一致      : 4161 / 4161
12ppem 墨迹集合逐格一致  : 4161 / 4161
24ppem 墨迹外框一致      : 4161 / 4161
24ppem 墨迹集合逐格一致  : 4161 / 4161
DEFAULT 质量下抗锯齿像素  : 0
```

即：**全部 4161 个字，在 Word 的渲染器里画出来的像素与设计位图逐格相同**；
12ppem（=9pt @96dpi）是 1:1，24ppem（=18pt）是精确 2 倍；
而且在本机**字体平滑开启**的情况下，抗锯齿像素仍然是 0（纯单色）。

判据分两层，是因为它们对系统设置的敏感度不同：
**墨迹外框**与抗锯齿无关、任何系统上都必须成立；
**墨迹集合逐格一致**在强制单色渲染（`NONANTIALIASED`）下必须成立——这量的是
**字体文件本身**的像素化行为，与系统"字体平滑"开关无关。

**比较器做过阴性对照。** 上面这组"全绿"只有在比较器**不是恒真**时才有意义，
所以用同一套 `GdiCanvas` + 同一套比较函数，故意喂进改错的设计位图，
确认它必须报不一致（18 项对照全部通过）：

| 对照类型 | 注入的错误 | 期望 |
|---|---|---|
| 阳性 | 真设计位图 | 判为一致 |
| 阴性 | 抽掉 1 个墨迹格 | 判为不一致 |
| 阴性 | 把 3 倍缩放当 2 倍 | 判为不一致 |
| 阴性 | 把 12ppem 结果冒充 24ppem | 判为不一致 |
| 阴性 | 整体平移 1 格 | 判为**一致**（归一化后形状不变 → 证明判据只比形状、不比画布绝对位置） |

最后一行是**反向**对照：它证明归一化确实抹掉了位置差异，
所以"一致"不是因为两个集合碰巧画在同一处。

逐码位明细落在 `reports/gdi_raster_scan.tsv`（4161 行，可直接 grep 任意码位），
主报告 `reports/gdi_compat.json` 只留结论与失败明细——避免 4161 条记录把主报告撑到 1.4 MB。

### 7.4 `tools/fontgen/verify_all.py`

第 8 步接入 Windows 兼容性检查（非 Windows 平台自动跳过，不影响跨平台流水线）。

### 7.5 "逐格一致"是**渲染器相关**的结论，不要外推

上面那组"4161 / 4161"量的是 **GDI**（Windows 文字渲染，Word 在 Windows 上走的就是它）。
换一个栅格化器，结论不一样：

| 渲染器 | 路径 | 12px | 24px+ |
|---|---|---|---|
| **GDI**（Windows / Word） | `TextOutW` + 24bpp DIB | **逐格一致（4161/4161）** | **逐格一致（4161/4161）** |
| FreeType（Pillow / Chrome / Linux） | `FT_LOAD_TARGET_MONO` | 有偏差：抽样 321 字平均 21.58 px/字（最坏 44） | 偏差 0，精确 |

FreeType 在 12px 下会做网格拟合（hinting），把 1px 竖画吸附撑粗。
这是**"用轮廓实现像素字"这一格式的固有属性**，不是字体文件有错——
文件里存的轮廓本身经全量反解校验与源位图逐格一致（`verify_ttf()`，
4161 个字形全部落在像素网格上）。

所以本节结论的适用范围是明确的：
**在 Windows 的 Word 里可用且像素级精确**；
跨到 Chrome / Linux 的 12px 小字场景，轮廓实现会掉精度，
那种场景请用随包提供的 BDF 与图集（那是真正的 1-bit 点阵）。

```bash
# 全链路复核 (8 步)
python tools/fontgen/verify_all.py

python tools/fontgen/verify_gdi.py
```

`verify_gdi.py` 的报告写到 `reports/gdi_compat.json`（含每个 charset 的选择结果、
12ppem/24ppem 全字符集的逐格比对计数与抗锯齿像素数）；
逐码位明细另存 `reports/gdi_raster_scan.tsv`。

## 9. 在 Word 里正确使用这个字体（速查）

0. **先覆盖安装。** 本机已安装的那份是 2026-10-23 的旧版（元数据错误的那版），
   家族名与新版相同；不覆盖的话 Word 命中的仍是旧的。
   完整安装步骤见 [`docs/install.md`](install.md)。
1. **字号用 9 / 18 / 27 / 36 pt**（100% 缩放；150% 缩放用 12 / 18 / 24 / 30 / 36 pt）。
   其它字号是缩放结果，不会是原来的像素。
2. **中西文都选中本字体**：Word 的字体下拉里选一次，字体对话框的"中文字体"和
   "西文字体"两栏都要是 PixelFont PC98 12。
3. **想要硬边像素**：把 Windows 的"字体平滑"设为"无"（系统级，影响所有程序）。
4. **缺字已经补齐**（2026-10-24，字符集 4161）：中文弯引号、全角空格、箭头、
   数学符号、全角括号都在字体里了，不再走回退。
5. 排版类需求请优先用 **BDF**（逐像素位图）或 **PNG 图集**——那两者是逐像素校验过的，
   不经过任何缩放。
