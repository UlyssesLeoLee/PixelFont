# 字形身份校验 —— 用独立开源像素字体逐字验证

**目标**：用**独立来源**的开源免费像素字体逐字比对，确认本字体每个码位渲染的
确实是**正确文字**的像素风，并发现、修复异常。

**结果摘要**：

| 项 | 结果 |
|---|---|
| 校验字符数 | 4140（ASCII 95 + 标点 35 + 假名 255 + 汉字 3755） |
| **身份错误**（画的不是这个字） | 目视复核**发现 1 例**（`U+3099 ゙` 浊点被画成半浊点的圈）→ 已由字符身份规则自动修掉；**修复后 0 例**，自动化 `OWN_COLLIDE` 检查**汉字 0 例** |
| 整字白块（字腔全失） | **119 → 0**（汉字），4 个假名是 PC-98 画风本身没有封闭腔 |
| 结构劣化 | 目视确认劣化 **32** 个 → 换源后 **26 个与参照完全一致**，其余 6 个差距 1–7（换源前是 15–36） |
| 硬检查命中 | **64 条，error 2 / warn 62**（`STRUCTURE_OUTLIER` 41 / `COUNTER_LOST` 13 / `OWN_COLLIDE` 7 / `EXACT_COLLIDE` 3） |
| 修复后全量回归 | 4140 字 / 43 批 **0 error 0 warn**；连续两次构建产物 sha256 逐字节一致 |
| 最终字体的目视覆盖 | 4140 字里 **4075 个与被复核版本逐像素相同**，其余 **65 个**（换源所致）另有定点重核：**65/65 全过，0 身份错误 / 0 确认劣化 / 3 存疑** |
| 字体来源 | SimHei（汉字兜底） + MS Gothic（PC-98 点阵） + **Fusion Pixel 12px 简体**（OFL-1.1 + Cubic 11 + Galmuri，开源免费，已裁剪入库 746 KB） |

---

## 1. 为什么必须做这件事

项目里一直有**两套互相证明**的验证：

1. `build_font.py` 的 `verify_bdf` / `verify_atlas` / `verify_ttf` 是**自证**：
   产品 == 源位图，源位图 == 产品位图。产物自洽，**全错也自洽**。
2. 上一轮 lane 的"源位图互比"是**同源**的：拿 SimHei 的一棵树栅格化成标准，
   拿 SimHei 的另一棵树栅格化成标准 —— 测的是"SimHei 有没有被栅格化坏"，
   而不是"这个字形本身对不对"。

真正的"两个字是不是同一个字"，必须拿**外部独立来源**的字形当标准。

## 2. 为什么不能全自动判定

试过用跨字体的**自动形状相似度**做逐字身份判定，**做不到**：

| 特征 | ASCII 命中率 | 假名命中率 | 汉字命中率 |
|---|---|---|---|
| 3×3 + 5×5 密度 | 52.1% | 37.5% | 7.5% |
| 8×8 密度 | 25.5% | 26.7% | 0.8% |
| 16×16 原始像素 | 41.5% | 35.0% | 3.3% |
| IoU 精排 | 53.2% | 25.0% | 4.2% |
| 跨字体轮廓 IoU | — | — | 0.0% |

汉字这一档的候选池有两万多个，而不同汉字的密度分布彼此高度相似，
逐像素又会被画风差异淹没 —— 指标分辨力不够，拿它判身份是在**制造假结论**。

所以分工是：

- **自动化**：做**与指标无关**的硬检查（位图完全相同 / 覆盖率 / 结构离群 / 字腔丢失）
  —— 目的是**筛高危**，不是替代目视。
- **目视比对**：生成并排对照表，由子代理逐批复核"我们画的到底是不是这个字"。

工具：`tools/fontgen/verify_identity.py`（提取与比对）、
`tools/fontgen/compare_refs.py`（对照表 + 硬检查）、
`tools/fontgen/gen_glyphcmp_sheets.py`（PNG 对照图）。

### 为什么对照载体是 PNG 而不是 ASCII 艺术

ASCII 点阵每字约 1 KB，4140 字就是 4 MB；PNG 一张 96 字只要约 1.4k token。
44 张对照图（`reports/glyphcmp_png/glyphcmp_000..043.png`）覆盖全部 4140 字。

## 3. 自动化硬检查的判据

| 判据 | 含义 | 实测分辨力 |
|---|---|---|
| `OWN_COLLIDE` | **我方**两个码位渲染成完全相同的位图 | **可靠**（两个汉字撞在一起 = 身份错误） |
| `COUNTER_LOST` | 参考字体的这个字有字腔，我方一个都没有 | **可靠**（能抓"整字塌成白块"） |
| `EXACT_COLLIDE` | 我方位图与参考字体的**另一个**码位逐像素完全相同 | 告警级（撞上的码位多半不在我们字符集里，是 Unicode 的同形异义码位） |
| `STRUCTURE_OUTLIER` | 横/竖笔画数与参考差得离谱（**绝对阈值 ≥ 12**） | 告警级 |
| `STYLE_DIFF` | 墨量差异 | **只记录，不下判定**（见下） |

### 被否掉的一条判据：平均墨量

最初的硬检查里有"墨量"一项，比的是**包围盒内平均墨量**。它是错的：

- 我们的 `!` 是 10×1 的框里 8 个墨点（均值 0.80），Ark 的 `!` 是 8×6 的框里 7 个墨点
  （均值 0.15）—— 差 +0.65，**纯属包围盒面积造成的伪影**，却让 128 个字全部误报。
- 换成"墨量像素数相对差"之后误报数一样高（十 / 个 / 火 / 巾 / ％ / * 全被抓出来），
  因为这些字的墨量差异是**合法的画风差异**，不是身份问题。

**结论：墨量对身份判定没有分辨力**，降级为描述性指标（`STYLE_DIFF`），不参与判定。

### 真正有分辨力的指标：字腔数

字腔是**拓扑**的 —— 腔还在就是还在，填死了就是 0，与面积无关。
用"参考字体的这个字有 N 个腔、我方有 0 个"作判据，在 3 套独立参考上一致命中 119 个字，
目视确认这些字**全部**是白块（量 / 置 / 叠 / 膏 / 舅 / 亮 / 亭 / 停 / 篇 / 噪 / 掌 / 事…）。

字腔定义（写在这里，避免各工具实现漂移）：
**4 邻域**下被墨迹完全包围的白区连通分量数，按墨迹**外接矩形**计；
任何碰到外接矩形上下左右任一边界的白区**不算腔**（那是外部背景）。

### 为什么 `STRUCTURE_OUTLIER` 必须用绝对阈值

最初用 z-score（MAD 尺度）。问题：**z-score 的尺度会随分布集中而收紧**——
字体变好 → 分布变集中 → MAD 变小 → 同样 6 倍标准差对应的**绝对**偏差门槛跟着收紧 →
离群数**不降反升**。实测：换成逐字选源后，绝对阈值 |差|≥12 的汉字从 204 降到 63，
而 z-score 判据的命中数却从 17 涨到 151 —— 那是**量具在骗人**，不是字体变差。

跨版本比较必须用绝对量，所以固定阈值 12。
12 的来由：被填死的字比参考少 20 多个竖笔分段（量 −28 / 舅 −24 / 暴 −22），
正常字只差 1–3 个；12 落在两者之间。

### 字腔数这个量具本身也验过

`count_holes` 是整条链的地基（路由推导、硬检查、缺陷判定全靠它）。它用**并查集**
写了一份**完全不同的第二实现**做交叉验证：

- 400 个汉字 × 2 个源 = **800 次**比较 → **0 处不一致**
- 参考字体抽样 **2286** 个字形 → **0 处不一致**

> **第一版并查集校验器自己写错了**：它把"同时贴到字形外接矩形边界的白区"也算成了腔，
> 800 次里 667 次不一致。修法是"先标出所有含边界格的根，再把这些根整体排除"。
> **量具自己也会撒谎** —— 交叉验证必须用真正不同的代码路径，
> 而且校验器写错时的表现和被测对象错时**一模一样**。

同一类教训在复核 lane 里也重演过：一条 lane 的 `holes()` 把 `q.append((y, nx))`
写成了 `q.append((y, nx))` 的行变量版（应为 `(ny, nx)`），竖直邻居被漏掉，
腔数被低估 —— 它错的时候同样"看起来完全正常"。

## 4. 参考集：独立票数只有 2 票，而且发现了一个更严重的问题

早先的清单说参考集有"Ark + Zpix + Unifont = 3 票"。**实测下来这句话是错的**：

```
ark-pixel-zh_hans vs fusion-pixel-zh_hans
  共有 3605 字   结构距离均值 0.00   中位 0.0   |差|>=12 的占比 0.0%
```

**Fusion Pixel 的简体版与 Ark Pixel 逐个汉字完全同构**（它缝进去的 Cubic 11 /
Galmuri 落在日文与韩文变体上，简体变体没用到）。所以 Fusion 对简体字
**不提供任何独立票** —— 12px 层面实际只有 **Ark + Zpix = 2 票**。

更要紧的是：**引入 Ark Pixel 作生产源之后，Ark 票也变成自证的**。
拿生产源自己当基准，比对就变成了自己和自己比。

因此本轮的参考列改为 **Zpix + Unifont**（都与生产源独立），
硬检查的默认参考集也一并改成 `--refs zpix,unifont-16`。

代价与取舍（实测数据）：

| 我方 vs | 结构距离均值 | 完全吻合 | 12px 笔画数可比的字 |
|---|---|---|---|
| Ark Pixel | 4.17 | 1208 / 3605 | 是 |
| Fusion Pixel | 4.44 | 1212 / 3755 | 是 |
| **Zpix** | **6.62** | **225 / 3755** | 是 |
| Unifont 16px | 30.87 | 0 / 3755 | 否（分辨率不同） |

Zpix 画风比 Ark/Fusion 粗犷，**像素级**一致率低得多 —— 所以目视复核的判定口径
相应改成"**按骨架判，不按像素判**"（见 [`glyph-review-protocol.md`](glyph-review-protocol.md)）。

### 循环论证的风险，量化过了

路由推导的"裁判"是 median(Ark, Fusion, Zpix) —— 实质是 Ark 两票。
对被判给 Ark 的 1043 个字，这等于"用 Ark 选 Ark"。实测换独立裁判 (Zpix) 重判：

- **882 个（84.6%）**：Ark 仍然更近 → 结论站得住，只是需要换个理由；
- 161 个：SimHei 略微更近，但差距只有 **1–3**（离群阈值是 12）→ 实质无差别。

再用三种裁判（Ark×2+Zpix / 纯 Zpix / 两票中位）各推一遍，**独立指标完全相同**：
我方 vs Zpix 距离均值都是 6.62，汉字丢腔都是 13 个，确认劣化覆盖都是 29/29。
**裁判口径的选择对结果没有实质影响**，因为决定性的差异都远大于判据噪声。

### 5.1 第二轮（修复后）复核冒出来的方法学收获

这一轮是**修复之后**做的复核，所以它同时验证了两件事：修复是否有效，
以及"目视到底能看出什么"。四条值得记下来的：

1. **量具被自检否决，并且如实记为"已否决"**。
   lane4 试了四个自动化筛查（原始 IoU 身份屏、归一化 IoU 身份屏、行墨迹剖面屏、
   横画计数屏），**对照试验显示它们的假阳性率与真阳性率相当**
   （例：行剖面屏自检命中 168，对照组（参考互比）命中 202）——
   也就是**没有分辨力**。lane4 把这四个屏的数字全部作废、不用于任何判定，
   只在报告里如实记下"已否决"。这与本项目反复遇到的那类坑是同一类：
   **量具错的时候，表现和对的时候一模一样。**

2. **格位映射要独立复核**。
   lane5 用"把 index 里的字用微软雅黑 20px 渲染成模板，与 PNG 每格自带的标签做
   互相关，argmax 应等于 index 码位"验证了 480/480 格；
   lane4 用 576×576 的标签-字符匹配矩阵也验证了一遍（对照试验 margin ≥ 0.090、
   0/576 负例）。
   **这一步抓到了旧报告的一个系统性误读**：旧轮把 U+78E8 读成「磨」并判为劣化，
   实际该格是「磿」—— 标签 vs U+78E8 的 IoU 0.666、vs U+78EB（「磨」）0.332，
   我方 vs Zpix 0.915，**三列一致，不是身份错误**。
   没有这一步，一个误读会一路污染到结论里。

3. **腔数指标会漏掉"部件内部横画并成实心带"**。
   lane4 找出的「盲」「惧」「看」，都是「目」塌成了「日」（内部少一条横）——
   腔数只差 1（2 vs 3），阈值筛不出来，是逐像素比对 16×16 位图才发现的。
   同理「舅」的「男」里的「田」塌成开口冂，腔数 4/4/4 与参考**持平**，完全抓不到。
   → **目视复核不是"复核一遍自动判据"，它能看见自动判据看不见的东西。**

4. **参考字体自己也会有重复位图**。
   lane5 查到 5 处我方位图与参考字体的另一个码位逐像素相同，
   全部是 **Ark Pixel 自己把汉字与其部首码位画成了同一张位图**
   （鸟/齐/犬/人/山）—— 是参考字体的属性，不是我们的错字。
   `EXACT_COLLIDE` 判据因此按"撞上的码位在不在我们的字符集里"分级。


## 6. 发现的异常与处理

### 5.2 最终字体与"被复核那一版"的差异：65 个字，补了一次定点重核

8 条 lane 复核的是 18:59 出的对照图（那时是 C4 + Ark 源）。之后又改了两处源：

1. 目视结论回灌：32 个确认劣化字强制换源 + 1 个字符身份修正（`U+3099 ゙`）；
2. 第三个生产源 Ark Pixel → Fusion Pixel（覆盖从 3990 补到 4140）。

所以最终字体与被复核那一版**有 65 个码位不同**。这件事必须量出来，不能靠"改的应该不多"：

```
逐码位比较两个版本「我方那一列」的位图（从栅格化器直接取 —— 与对照图上画的
是同一份数据，各 lane 的抽取自检证明过这点：抽出来放大贴回原 PNG 逐像素一致）
→ 65 / 4140 不同，其余 4075 个逐像素相同
```

- 差异清单：`reports/glyphcmp_review/changed_since_review.txt`
- 定点重核图：`reports/glyphcmp_review/fixed/glyphcmp_000.png`（33 字）、
  `reports/glyphcmp_review/fixed2/glyphcmp_000.png`（32 字）
- 定点重核结论：`reports/glyphcmp_review/fixed_review.{json,md}`

**定点重核的结果：65 / 65 全过，身份错误 0，确认劣化 0，存疑 3**（`゙` / `糯` / `衅`）。
换源确实把之前画不好的字修好了：酱 / 鳖 / 誊 / 蛰 / 嘎 / 撬 / 橇 这 7 个
（此前两个源都画不好）现在**部件全部在位** —— 鳖 的「鱼」部「田」已恢复四格分隔，
誊 的「言」部、撬/橇 的「毳」三毛均可数。

复核的严谨性（都写在该 lane 的报告里）：
- **列映射是实证的**，不是照抄表头：按出图工具的几何从 PNG 反解三列，
  第 1 列 65/65 与当前构建的位图逐像素相同、第 3 列 65/65 与 Unifont 相同。
- **量具两份独立实现**，65 个字形上 0 分歧，扩到 800 个参考字形仍 0 分歧。
- **身份碰撞全库扫描**：65 个我方位图与「我方全字库 4140 + Zpix 22228 + Unifont 58909」
  按（形状，字节）归并比对，与任何别的码位逐像素相同者 **0 个**。
- **构建完整性**：65 个我方位图与 `vendor/fusion-pixel-12px` 裁剪版在 12px 的渲染
  **逐字节相同 65/65**（整格与墨迹框都比）—— 路由确实生效，切源/裁剪/基线没有引入额外偏差。
- **两个「逐字节相同」别混**（这条 lane 替我抓出了 brief 里的一个错）：
  - *最终字形 vs 源头字体* = 65/65 相同 —— 证明切源精确；
  - *旧版本 vs 新版本* = 0/65 相同 —— 这 65 个字的旧源是 SimHei 49 个 + MS Gothic 16 个，
    **换了字族，位图必然变**。只有 Ark → Fusion 那种同族替换才是位图不变。

**比较时踩了一个坑，值得记下来**：旧名单里第三源的键叫 `"ark"`，新代码里改名成
`"fusion"`；用旧名单直接建栈时，`sources["ark"]` 取不到 → 那 1108 个码位**回退到了
SimHei** → 误报"1108 个字变了"。核对发现 Ark 与 Fusion 摆出来的位图**逐像素相同**
（度量 / ascent / advance / lsb / 墨迹框 / 像素全同），把旧名单的 `"ark"` 映射成
`"fusion"` 才得到真实的 65。
→ **量具对不上时，先怀疑量具**：1108 与 65 差一个数量级，明显不是"换源改了这么多字"。

### 6.1 身份错误：0 例

**没有任何一个码位画成了错误的字。** 这是本轮校验最重要的结论。

自动化层面的机械印证：新增的 `OWN_COLLIDE` 检查（我方两个码位渲染成完全相同的位图）
命中 8 组，**全部是标点/符号天然同形**（`'` 与 `,`、`.` 与 `·`、`・` 与 `.`、
`_` 与 `—`、`` ` `` 与 `､`、`゙` 与 `゜`、`｡` 与 `ﾟ`），**汉字 0 例**。

### 6.2 整字塌陷：119 → 0

根因：源字体 SimHei 是**平滑轮廓字体**，12px 下密笔画汉字的部件横画会粘连，
把「日」「目」「田」这类部件的字腔整个填死 —— 整字渲染成一块白块。

以「量」为例（12×12 外接框）：

```
我方 (SimHei MONO)          Ark Pixel 12px
.########.                 .#########..
.########.                 .#.......#..
.########.                 .#########..
##########                 .#.......#..
.########.                 ###########.
.########.                 .#...#...#..
.#..#...#.                 .#########..
..######..                 .#...#...#..
.########.                 .#########..
##########                 .....#......
                           ###########.
```

上半部「日」整个被填实。我方 10×7 全部是实心墨。

**为什么不是换二值化阈值就能解决**：实测了 5 种栅格化策略（FreeType MONO、
灰度 128/144/160/176），以"字腔数均值"打分：

| 策略 | 字腔均值 | 参考 | dcol 中位 | dcol ≤ −18 的字 |
|---|---|---|---|---|
| **MONO（当前）** | **2.30** | 2.39 | **−4.0** | **24** |
| 灰度 128 | 1.16 | 2.39 | −6.0 | 113 |
| 灰度 144 | 0.61 | 2.39 | −8.0 | 202 |
| 灰度 160 | 0.25 | 2.39 | −10.0 | 440 |
| 灰度 176 | 0.08 | 2.39 | −13.0 | 916 |

**MONO 反而是最好的**（FreeType 的 hinting 把笔画吸附到像素格，保住了 1px 粗细）。
而且 SimHei 的「日」在 12px 只有 4 行 —— 3 横 2 腔根本放不下，
**这是源字体在该尺寸的固有极限，不是阈值问题**。

### 6.3 选源规则：从"只切白块"到"逐字选源"再到"三源兜底"

最初的判据是"SimHei 渲染出 0 腔 → 切到 MS Gothic"（blob 模式），
只能覆盖**整字**塌陷。但目视复核认定的问题**多数是局部塌陷**
（某个部件被填死，整字还有腔）—— blob 模式一个都抓不到。

**第二步：逐字选源。** 对每个汉字比较各源的结构签名
（字腔数 / 竖笔画分段数 / 横笔画分段数）离参考字体的距离，取更近者。

距离函数：

```
距离 = w×|字腔差| + |竖笔差| + |横笔差|
```

**w 的取值是标定出来的**，不是拍的。理由：字腔是**拓扑量**，不受字宽与分辨率影响；
横/竖笔画分段数则对参考字体的分辨率与字宽天然有偏。

| w | 切换数 | 确认劣化覆盖 | 存疑覆盖 | 字腔达标 | 腔差均值 |
|---|---|---|---|---|---|
| 1 | 2032 | 20/21 | 18/30 | 83.8% | 0.703 |
| **4** | **1952** | **20/21** | **19/30** | **86.4%** | **0.623** |
| 12 | 1859 | 18/21 | 17/30 | 87.6% | — |
| 纯字腔优先 | 1857 | **18/21** | 17/30 | 87.6% | 0.586 |

选 **w = 4**。纯字腔优先（字腔差不等就只看字腔）**反而丢 2 个确认劣化字**
（羹 U+7FB9、霍 U+970D）—— 它们的字腔数本来就对，塌的是**笔画**，
所以笔画分段数必须留在判据里，不能让字腔一票否决。

**再加一条字腔硬约束**：参考字体说这个字该有腔，而某个候选源渲染出 **0 腔**
（整字白块），另一个候选源有腔 —— 那就**必须**选有腔的那个，不看笔画数差多少。
理由：0 腔是**可见的硬错误**，笔画数差只是风格差异。
实测这条约束修掉了 blob 模式下漏掉的「粔」U+7CD5（不加约束时它被判给 SimHei，0 腔白块）。

**第三步：引入第三个源。** 双源仍然解决不了根因 —— MS Gothic 是 JIS 汉字的
PC-98 点阵，简体专有字一个都没有；这些字只能退到 SimHei 的平滑轮廓，
而它在 12px 下会把整字糊成白块。于是把 **Ark Pixel 12px**（OFL-1.1，开源免费）
也作为生产源，按同一条规则参与竞争。

**最终规则（C4）**：

> 双源优先（SimHei / MS Gothic）。
> 只有当 **MS Gothic 根本没有这个字形**，或**两个源都渲染成 0 腔白块**时，
> 才让 Ark Pixel 参与竞争。

为什么不是"三个源全程竞争"：那会让 Ark 接管 3440 个汉字（92%），
字体画风整体从"SimHei 栅格化 + PC-98 点阵"变成"现代中文像素字体为主"，PC-98 味基本消失。
实测 C4 规则已做到 汉字白块 0 / 确认劣化全覆盖，剩下 2440 个字没有必要动。

**最终路由名单**：

| 项 | 数值 |
|---|---|
| 模式 | `per_char`（逐字选源）+ C4 候选池规则 + 字符身份规则 + 目视强制覆盖 |
| 字腔权重 | 4 |
| 切走 | **3010** 个码位（MS Gothic **1902** + Fusion Pixel **1108**） |
| 保持 SimHei | 745 |
| 与参考的结构距离均值 | 11.28 → **4.39** |
| 与参考完全吻合的汉字 | 21 → **1211** |

名单存在 `tools/fontgen/ideo_route.json`，
由 `tools/fontgen/derive_ideo_route.py --per-char --hole-weight 4` 重新推导，
**不靠人肉维护一张表**。

### 6.4 规则必须只有一份实现

推导脚本、构建门禁、诊断工具（`explain_route.py`）现在共用
`tools/fontgen/route_rule.py` 里的**同一份**规则实现（候选池规则 + 距离函数 + 字腔硬约束）。

为什么：门禁要复核"当初那个选择现在还成不成立"。如果门禁用另一套判据，
它检查的就是一件不存在的事 —— 门禁会一直报"切源理由不成立"，
而真实原因是**判据自己改过**。同理，诊断工具给出的解释必须和构建结果一致，
否则人会被工具带偏。

### 6.5 第三个源的生产化

**第三个源为什么是 Fusion Pixel 而不是 Ark Pixel**：实测 Fusion 的简体版与 Ark 的
**结构**完全相同（3605 个共有汉字逐个一致），但**覆盖**多 12054 个码位 ——
它把 Ark / Cubic 11 / Galmuri 缝进了同一套字重体系。对我们 4140 个码位：

| 源 | 覆盖 | 与 Ark 的位图关系 |
|---|---|---|
| Ark Pixel 12px 简体 | 3990 / 4140（缺 150） | — |
| **Fusion Pixel 12px 简体** | **4140 / 4140** | 共有部分 **3989/3989 逐字节相同** |

所以把生产源从 Ark 换成 Fusion：**对 3989 个字零画风变化**，
却让原先没得选的 150 个字（酱 / 誊 / 鳖 / 蛰 / 嘎 / 撬 / 橇 …）有了真正的点阵字形。
实测那 7 个当时仍未修的字，换源后与**独立**参考 Unifont 的结构距离：

| 字 | Fusion | Zpix | SimHei | MS Gothic |
|---|---|---|---|---|
| 蛰 | **30** | 29 | 56 | — |
| 嘎 | **35** | 36 | 58 | 59 |
| 酱 | **44** | 43 | 69 | — |
| 誊 | **44** | **37** | 67 | — |
| 鳖 | **56** | **56** | 89 | — |
| 橇 | **71** | **67** | 86 | 79 |
| 撬 | **73** | **70** | 89 | 76 |

（Zpix 的字形是 **13 宽**，放不进我们 12px 的全角格，所以它当不了生产源。）

**生产源为什么入库**：参考字体只用于校验、不参与构建，所以不入库；
而生产源**参与构建**，不入库就等于"构建依赖这台机器上恰好下载过它"，
换台机器构建不出同一个结果。裁剪到本项目 4140 码位后 **763 556 字节**，
三份许可证（Ark Pixel OFL / Cubic 11 OFL / Galmuri LICENSE）一并入库
（`vendor/fusion-pixel-12px/LICENSES/`）。

`tools/fontgen/vendor_fusion_pixel.py --check` 做两项验证，缺一不可：

1. 裁剪前后的渲染**逐像素一致**（实测 **4140** 个字形，0 处不一致）；
2. 裁剪版的 cmap == 原字体 cmap ∩ 本项目字符集。

> 坑：`fontTools.subset --unicodes` 收的是**十六进制码位**，写成 `U+4E01`
> 会被静默忽略一部分 —— 那 150 个码位随后退化成 `.notdef`，
> 而 `.notdef` 是空心豆腐框、自带 1 个"字腔"，会把"这个源能画"变成假阳性。

**基线归一化**：Ark 的 ascent 是 10（它把汉字占满 12 行整格），SimHei/MS Gothic 是 11。
`BitmapFont` 新增 `cell_ascent` / `cell_descent`：改的是**格子几何**，
字形仍按源字体自己的 offset 贴。实测：

| 源对 | 墨迹范围完全一致的比例 |
|---|---|
| Ark vs MS Gothic | **89.1%** |
| MS Gothic vs SimHei（现有双源） | 68.0% |

也就是说，引入 Ark 之后基线一致性**反而比原来的双源更好**。

### 6.6 C4 规则的代价：量化过了

C4 规则让 Ark Pixel 只在"MS Gothic 没这个字形"或"两个源都画成 0 腔"时参与竞争。
代价是：**有些 MS Gothic 覆盖的字，Ark 的渲染其实明显更好，但 Ark 不被允许参与**。

用**独立参考**（Zpix，MIT，与生产源无亲缘）当尺子量这个代价 ——
不能用裁判本身（median(Ark, Fusion, Zpix) 是 Ark 主导的，用它比就是循环论证）：

| Ark 比当前选源更贴近 Zpix 的幅度 | 字数 | 其中当前是 MS Gothic | 其中当前是 SimHei |
|---|---|---|---|
| ≥ 2 | 1300 | 1003 | 297 |
| ≥ 4 | 810 | 600 | 210 |
| ≥ 8 | **295** | 215 | 80 |
| ≥ 12 | 104 | 63 | 41 |
| ≥ 16 | 34 | 23 | 11 |

295 个字（占汉字 7.9%）在独立口径下 Ark 明显更好。典型例子：

| 字 | 当前源 | 我方签名 | Ark 签名 | Zpix 签名 |
|---|---|---|---|---|
| 露 U+9732 | MS Gothic | (3, 41, 26) | (10, 44, 27) | (10, 44, 27) |
| 叠 U+53E0 | MS Gothic | (5, 28, 19) | (6, 43, 21) | (6, 45, 21) |
| 啊 U+554A | MS Gothic | (1, 15, 33) | — | — |

差距是**结构性的**（腔数差 5、7），不是画风差异。

**但结构性差异 ≠ 目视劣化**：目视复核在 576 字里只确认了 1 例（叠），
其余 33 例判为存疑。所以**不能用这条结构判据去批量改源** ——
那会让 295 个字按一个**筛查指标**换源，而不是按**目视判断**换源。
（自动判据的定位是筛高危，不是替代目视 —— 见 6.7。）

### 6.7 目视结论接回自动推导：一条通道，而不是一张人肉表

目视是唯一能发现**部件级塌陷**的手段（「叠」的「且」框被填实，但全字腔数只差 1，
任何阈值都抓不到）。但名单不能靠人肉维护 —— 所以把复核结论作为**推导的输入**：

```bash
python tools/fontgen/derive_ideo_route.py --per-char --hole-weight 4 \
    --force-from-review reports/glyphcmp_review/summary.json
```

被确认劣化的字强制改用**更贴近参考**的源。选源规则不能是循环的：
裁判是 Ark 主导的，"离裁判最近的"对被判给 Ark 的字等于"总是选 Ark"。
所以用 **腔数封顶到参考值**后取最大的、再按距离决胜 ——
封顶的意义是"腔比参考**多**不加分"（「瓣」「雹」我方腔数反比参考多，那是错不是好）。

这条规则抽在 `route_rule.choose_forced`，**推导脚本与构建门禁共用同一份实现** ——
门禁要复算"当初那个选择现在还成不成立"，两边规则漂移的话，
门禁会判这些字"切源理由不成立"而**拒绝构建**（自审时真的踩到了）。

### 6.8 字符身份规则：我方把某个码位画成了另一个码位

这一类错误**距离判据完全看不见**：画错的字符与对的字符结构上就是同一个，
距离自然是 0。判据（`route_rule.identity_confused`，三条都要满足）：

1. 参照字体对两个码位的**字腔数不同** —— 参照能区分它们。
   若参照也画成同一个，那是该尺寸下天然同形，不是我们的错；
2. 我方这个码位的字腔数 == 参照对**另一个**码位的字腔数 —— 说明我方画的是那一侧；
3. 我方这个码位的字腔数 != 参照对它的字腔数。

实例：`U+3099 ゙`（浊点）与 `U+309C ゜`（半浊点）——
**MS Gothic 自己就把两个都画成 3×3 的圈**，我们忠实继承了；
而参照说 ゙ 该是 0 腔（两撇）、゜ 是 1 腔（圈）。
我方 ゙ 是 1 腔 == 参照的 ゜ → **把浊点画成了半浊点**，
这是目视复核发现的**唯一一个身份错误**（lane1，confidence high）。

规则跑出来的结果正好是它：**1 个修正**（U+3099 → Fusion Pixel，腔 1 → 0），
另外 5 组"同形"（撇号/逗号、下划线/破折号、反引号/半角句点、
中点/句点、半角句点/半浊点）**没有误动** —— 靠的就是第 1 条
（那些组参照也分不出，或只是风格差异）。

**门禁同步**：`identity_fix` 条目走另一条复算（所选源的字腔数须与参照一致，
且须与另一个可用源不同），否则门禁会用距离规则判"切源理由不成立"而拒构建。

### 6.9 局部塌陷：目视抓得到，自动抓不到

目视复核找出过 29 例**确认**的结构劣化（暴 / 爆 / 雹 / 鼻 / 瓣 / 矗 / 蠢 / 叠 …）
和 41 例存疑。这些是**部件级**的粘连：整字还有腔，但某个部件（日 / 雨 / 田 / 革）被填死。

检测极限（实测）：自动判据对这些**局部**塌陷的召回率只有 **5/29**。
原因见 6.10 的反例 —— 全字腔数完全看不出来。

**所以正确的分工是：自动判据筛高危，目视复核做最终判定。**
报告里必须写明这个检测极限，不能让人误以为自动检查已经覆盖了全部缺陷。

> 读这个召回率数字要注意：标定集是**修复前**的对照图上标的字。
> 修复之后大部分劣化字已经好了，自动判据自然不再报它们 → 召回率看起来"变差"。
> 跨版本比较必须看**修复前后的命中总数**（818 → 340 → 93 → **80**），
> 不能拿修复后的召回率去说"检测能力退步了"。

### 6.10 反例：自动判据为什么抓不到局部塌陷

- **瓣**（U+74E3）：我方字腔 **7** 个，参考 **5** 个 —— 我方**还多**；
- **雹**（U+96F9）：我方字腔 **6** 个，参考 **2** 个 —— 我方**还多**。

两个都被目视判为 DEGRADED。塌陷发生在**某一个部件**里，全字腔数完全看不出来。
所有基于腔数/方块面积的阈值都无法区分它们：

| 判据 | 命中总数 | 标定集命中 | 误报率 |
|---|---|---|---|
| 腔数差 ≥ 2 | 501 | 17/70 | 96.6% |
| 腔数差 ≥ 3 | 240 | 14/70 | 94.2% |
| 腔数比 < 0.6 | 521 | 15/70 | 97.1% |
| 最大实心方块比 ≥ 1.5 | 2082 | 21/70 | 99.0% |

### 6.11 构建门禁

`charset.gate_ideo_route()` 在每次构建时逐个核对名单里的字**仍然**满足切源理由：

- **签名比对**：重算各源的结构签名，与名单里记录的不一致就说明源字体版本变了
  → 切源依据已过期，拒绝构建；
- **切源理由复核**：用名单里记录的参考签名**按同一条规则复算一次**，
  确认"切过去确实更好"（或字腔硬约束）依然成立；
- 名单条目缺签名 / 指定的源已不含该字形 → 拒绝构建。

**门禁做过自检**（注入必须真的落地）：

```
注入: 把 U+4E01 名单条目的 sig_ideo[0] 从 3 改成 0 (伪造源字体版本变化)
结果: 构建被拒 (exit 1)
      "ideo 路由名单失效, 共 1 个码位:
         U+4E01 '丅' 结构签名与推导时不一致 (记录 ideo=[3,11,10]/alt=[0,12,10],
         现 ideo=[0,11,10]/alt=[0,12,10]) —— 源字体版本变了, 请重新推导名单"
恢复: 构建通过 (exit 0)
```

### 6.12 构建是可复现的

连续两次构建，产物的 sha256 **完全一致**：

| 产物 | sha256 |
|---|---|
| `PixelFontPC98-12.ttf` | `4C24D827FE9B23A4FD477128DE7B284700A9F4658060D65E45C136DE5FFAFCB9` |
| `PixelFontPC98-12.bdf` | `120417838B3ED5A038915BFEF6B44DE6DAA03A7EEEC8F17B527CB91B8C2FD6BD` |
| `PixelFontPC98-12-atlas.png` | `6B3EFDC708F89A9A05BB5A93FD75BAE4FBC91853E9DE5E8E4D4E7B9392C6646C` |

一开始做不到：两次构建只有 `head` 表的 `created` / `modified` 不同，
其余所有表逐字节一致 —— 差的就是这两个时间戳，但它每次都变，
就没法拿 sha256 校验产物。现在把它们钉死（可用 `SOURCE_DATE_EPOCH` 覆盖）。

这个性质有实际用处：生产源要从系统字体目录读（SimHei / MS Gothic），
而路由名单是**推导产物** —— 一旦某台机器的系统字体版本不同，产物就会变。
产物可复现，才能把"产物变了"和"源变了"区分开。

### 6.13 出图工具修了一个真缺陷

早期版本把槽位固定按 12px 算，而 Unifont 是 16px 字体，
它的墨迹**溢出槽位**串到下一格「我方」列的左缘 —— lane3 实测污染 111 格。
复核者看到的不再是干净的对照，这种污染会让人对同一个字得出不同结论。

现在槽位按**所有列的最大字形**算（16×16），并且每列都裁剪到自己的槽位。

## 7. 剩余的 2 条硬错误与 13 条告警

硬检查（独立参考集 Zpix + Unifont）命中 80 条，error 2 条：

| 码位 | 字 | 情况 | 结论 |
|---|---|---|---|
| U+8D8B | 趋 | 我方 0 腔，Zpix 2 腔 / Unifont 2 腔 | 我方用的就是 **Ark Pixel 的位图**（Ark 自己也画 0 腔），MS Gothic 没这个字。Zpix 与 Ark 在这个字上画法不同 —— **参考集画风分歧**，已逐字出图目视复核，字清晰可辨 |
| U+8206 | 舆 | 我方 0 腔，Zpix 7 腔 / Unifont 1 腔 | 同上（Ark 自己 0 腔） |

另有 13 条 `COUNTER_LOST` 告警：参考中位腔数只有 1，属 12px 下的边缘取舍
（Zpix 把「舆」的「田」闭上了，我们没闭）。**已逐字出图目视复核**：
埃 / 驰 / 邓 / 饿 / 颈 / 涟 / 氢 / 趋 / 疡 / 幼 / 舆 / 狱 / 制
——汉字全部清晰可辨，**不是缺陷**。

### 7.1 「0 腔」不等于「白块」——这个区分必须说清

Ark Pixel 缺 150 个汉字（GB2312 后半的简体字），这些码位只能回到 SimHei 的轮廓栅格化。
其中 13 个我方渲染出 0 腔，很容易被当成"又是白块"。按**墨量**逐个复核后：

| 字 | 我方墨量 | 参照腔数（ark/zpix/unifont） | 判定 |
|---|---|---|---|
| 柴 垫 岿 莉 恋 梁 蕊 淫 峦 执 纵 | 26%–35% | 0 / 0 / 0 | **结构上本就无封闭空间**，非缺陷 |
| 孪 | 26.3% | – / 1 / 0 | 边缘差异，需目视 |

墨量 26–35% 是**正常汉字**的密度（真白块接近 100%），三个参照也都画不出封闭空间。
所以这 13 个字既不是白块，也不是塌陷 —— 它们就是"这个字在 12px 下没有腔"。

**结论：汉字白块 = 0。** 剩下 2 条 error（趋 / 舆）是**参考集画风分歧**
（Ark 与 Zpix 在这两个字上画法不同），已目视复核为可辨。

## 8. 复现步骤

### 一条命令复核全部结论

```bash
python tools/fontgen/verify_all.py
```

它把下面 6 步串起来，每步都报出它**实际消费了什么**，任一步失败就明确说哪一步失败：

| 步 | 检查什么 | 判据 |
|---|---|---|
| 1 | 生产源自检 | Fusion Pixel 裁剪版与原字体**逐像素一致** + cmap 覆盖相符 |
| 2 | 构建 | 缺字门禁 + 路由名单门禁 |
| 3 | 全量回归 | 4140 字分 43 批，产物与源位图逐像素一致 |
| 4 | 字形硬检查 | 参考集 Zpix + Unifont（**与生产源独立**） |
| 5 | 产物与源同步 | **独立读 dist/** 与当前源逐字比对（不靠构建脚本自证） |
| 6 | 路由名单自检 | 按名单自述的输入重新推导，与入库名单比对 |

第 5 步单独存在的理由：构建脚本会自检"产物 == 源位图"，但那是**同一次运行内部**的自证。
真正会出事的是**改了名单却忘了重建**——那时产物还是旧的，而构建脚本根本不会被执行。
（工具：`tools/fontgen/verify_products.py`）

### 终检：全新 clone 独立构建

比"连续两次构建一致"更强的一步 —— **从远端重新 clone 一份，在那边独立构建**：

```bash
git clone --depth 1 --branch main https://github.com/UlyssesLeoLee/PixelFont.git
cd PixelFont && python tools/fontgen/build_font.py
```

结果：clone 里的构建**通过**，且与本地产物的 sha256 **逐字节一致**：

| 产物 | sha256（前 16 位） | 与本地一致 |
|---|---|---|
| `PixelFontPC98-12.ttf` | `FCC65BCBCD8A1A02…` | ✔ |
| `PixelFontPC98-12.bdf` | `7AA4A40E224B1121…` | ✔ |
| `PixelFontPC98-12-atlas.png` | `54D5D7820917287A…` | ✔ |
| `PixelFontPC98-12-atlas.json` | `8B1044491BE5C4E6…` | ✔ |

也就是说：**任何人 clone 仓库、照文档跑构建命令，得到的字体逐字节相同**。
这依赖三件事：字体头时间戳已钉死（`SOURCE_DATE_EPOCH` 可覆盖）、
生产源已入库（`vendor/fusion-pixel-12px/`）、路由名单是入库的推导产物。

### 逐步复现

```bash
# 1. 取参考字体 (开源免费, 不入库, 只记来源与 sha256)
python tools/fontgen/fetch_ref_fonts.py
python tools/fontgen/fetch_ref_fonts.py --verify

# 2. 生产源: 裁剪并验证 Fusion Pixel (入库)
python tools/fontgen/vendor_fusion_pixel.py
python tools/fontgen/vendor_fusion_pixel.py --check

# 3. 自动化硬检查 (注意 --json 才是 JSON 输出路径, --out 是 markdown 路径)
python tools/fontgen/compare_refs.py --screen-only \
    --refs zpix,unifont-16 \
    --json reports/glyphcmp_screen.json

# 4. 生成对照图 (槽位按最大字形算, 不会串格)
python tools/fontgen/gen_glyphcmp_sheets.py \
    --refs zpix,unifont-16 \
    --cols 12 --rows 8 --scale 2 \
    --outdir reports/glyphcmp_png --index reports/glyphcmp_index.json

# 5. 量具自检: 自动判据对着目视标定集的召回率
python tools/fontgen/calibrate_detector.py \
    --screen reports/glyphcmp_screen.json --review reports/glyphcmp_review \
    --out reports/glyphcmp_calibration.json

# 6. 汇总各 lane 的目视复核 + 与路由名单对账
python tools/fontgen/aggregate_glyphcmp_review.py \
    --out reports/glyphcmp_review/summary.json \
    --md  reports/glyphcmp_review/summary.md
python tools/fontgen/account_fixes.py

# 7. 重新推导路由名单 (换源字体版本后必须跑)
python tools/fontgen/derive_ideo_route.py --per-char --hole-weight 4

# 8. 构建 + 全量回归
python tools/fontgen/build_font.py
python tools/fontgen/regress_all.py
```

## 9. 已知限制

1. **独立票数只有 2 票**（Zpix / Unifont）。Cubic 11 的 4 个候选 URL 全部 404；
   Fusion 虽是缝合产物但实测与 Ark 同构，对简体字不提供独立票。
   而 Ark 现在是生产源，连它自己也退出了独立票序列 —— 这是本方法最根本的限制。
2. **参考集自身有分歧**：Ark / Zpix 在少数字上画法不同（趋、舆…），
   这类字只能靠目视定夺，本项目已逐个复核。
3. **局部塌陷**的自动检测召回率只有 5/29，只能靠目视发现（见 6.6）。
4. **Ark 缺 150 个汉字**（GB2312 后半的简体字），这些码位仍然只能用 SimHei 的轮廓栅格化，
   12px 下的塌陷风险无法根除。
5. Zpix 缺 12 个假名，这些码位在 Zpix 参考下**无法比对**。
6. 我方字体是 12×13 网格，Unifont 是 16×16 —— 纵向不可直接比像素，只比骨架。
7. MS Gothic 的假名（タ / ダ / ﾀ）在 PC-98 点阵里本来就没有封闭腔，
   与 Unifont / Zpix 不同 —— 属**画风差异**，不是缺陷。
