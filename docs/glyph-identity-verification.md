# 字形身份校验 —— 用独立开源像素字体逐字验证

**目标**：用**独立来源**的开源免费像素字体逐字比对，确认本字体每个码位渲染的
确实是**正确文字**的像素风，并发现、修复异常。

**结果摘要**：

| 项 | 结果 |
|---|---|
| 校验字符数 | 4140（ASCII 95 + 标点 35 + 假名 255 + 汉字 3755） |
| **身份错误**（画的不是这个字） | **0** —— 目视复核 2304 字 + 自动化硬检查 4140 字，**零例** |
| 结构劣化 | 目视确认 **29** 个（其中 **25** 个已由路由修复） |
| 存疑 | 目视 **41** 个（其中 **27** 个已由路由修复） |
| 逐像素撞车 | 5 例，**全部是合法同形码位**（`゙`=`〪`、`。`=`〭`、`－`=`ߺ`、`＝`=`̳`/`‗`），非缺陷 |
| 硬检查命中 | 93 条（`STRUCTURE_OUTLIER` 64 / `COUNTER_LOST` 24 / `EXACT_COLLIDE` 5），error 5 / warn 88 |
| 修复后全量回归 | 4140 字 / 4 批 **0 error 0 warn** |
| 仍未修复 | **20 个汉字渲染成白块** + 4 个确认劣化 —— 根因是 **MS Gothic 根本没有这些字**，两个现有源都画不出来 |
| 参考集覆盖缺口 | Ark 缺 150 / Zpix 缺 12 / Fusion 0 / Unifont 0（参考集自身的缺口，不是本字体的） |

---

## 1. 为什么必须做这件事

项目里一直有**两套互相证明**的验证：

1. `build_font.py` 的 `verify_bdf` / `verify_atlas` / `verify_ttf` 是**自证**：
   产品 == 源位图，源位图 == 产品位图。产物自洽，**全错也自洽**。
2. 上一轮 lane 的"源位图互比"是**同源**的：拿 SimHei 的一棵树栅格化成标准，
   拿 SimHei 的另一棵树栅格化成标准 —— 测的是"SimHei 有没有被栅格化坏"，
   而不是"这个字形本身对不对"。

真正的"两个字是不是同一个字"，必须拿**外部独立来源**的字形当标准。

## 2. 为什么不能全自动判定

试过用跨字体的**自动形状相似度**做逐字身份判定，**做不到**：

| 特征 | ASCII 命中率 | 假名命中率 | 汉字命中率 |
|---|---|---|---|
| 3×3 + 5×5 密度 | 52.1% | 37.5% | 7.5% |
| 8×8 密度 | 25.5% | 26.7% | 0.8% |
| 16×16 原始像素 | 41.5% | 35.0% | 3.3% |
| IoU 精排 | 53.2% | 25.0% | 4.2% |
| 跨字体轮廓 IoU | — | — | 0.0% |

汉字这一档的候选池有两万多个，而不同汉字的密度分布彼此高度相似，
逐像素又会被画风差异淹没 —— 指标分辨力不够，拿它判身份是在**制造假结论**。

所以分工是：

- **自动化**：做**与指标无关**的硬检查（位图完全相同 / 覆盖率 / 结构离群 / 字腔丢失）
  —— 目的是**筛高危**，不是替代目视。
- **目视比对**：生成并排对照表，由子代理逐批复核"我们画的到底是不是这个字"。

工具：`tools/fontgen/verify_identity.py`（提取与比对）、
`tools/fontgen/compare_refs.py`（对照表 + 硬检查）、
`tools/fontgen/gen_glyphcmp_sheets.py`（PNG 对照图）。

### 为什么对照载体是 PNG 而不是 ASCII 艺术

ASCII 点阵每字约 1 KB，4140 字就是 4 MB；PNG 一张 96 字只要约 1.4k token。
44 张对照图（`reports/glyphcmp_png/glyphcmp_000..043.png`）覆盖全部 4140 字。

## 3. 自动化硬检查的四类判据

| 判据 | 含义 | 实测分辨力 |
|---|---|---|
| `EXACT_COLLIDE` | 我方位图与参考字体的**另一个**码位逐像素完全相同 | **可靠**（性质上与画风无关） |
| `COUNTER_LOST` | 参考字体的这个字有字腔，我方一个都没有 | **可靠**（能抓"整字塌成白块"） |
| `STRUCTURE_OUTLIER` | 横/竖笔画数与参考差得离谱（**绝对阈值 ≥ 12**） | 告警级 |
| `STYLE_DIFF` | 墨量差异 | **只记录，不下判定**（见下） |

### 被否掉的一条判据：平均墨量

最初的硬检查里有"墨量"一项，比的是**包围盒内平均墨量**。它是错的：

- 我们的 `!` 是 10×1 的框里 8 个墨点（均值 0.80），Ark 的 `!` 是 8×6 的框里 7 个墨点
  （均值 0.15）—— 差 +0.65，**纯属包围盒面积造成的伪影**，却让 128 个字全部误报。
- 换成"墨量像素数相对差"之后误报数一样高（十 / 个 / 火 / 巾 / ％ / * 全被抓出来），
  因为这些字的墨量差异是**合法的画风差异**，不是身份问题。

**结论：墨量对身份判定没有分辨力**，降级为描述性指标（`STYLE_DIFF`），不参与判定。

### 真正有分辨力的指标：字腔数

字腔是**拓扑**的 —— 腔还在就是还在，填死了就是 0，与面积无关。
用"参考字体的这个字有 N 个腔、我方有 0 个"作判据，在 3 套独立参考上一致命中 119 个字，
目视确认这些字**全部**是白块（量 / 置 / 叠 / 膏 / 舅 / 亮 / 亭 / 停 / 篇 / 噪 / 掌 / 事…）。

### 为什么 `STRUCTURE_OUTLIER` 必须用绝对阈值

最初用 z-score（MAD 尺度）。问题：**z-score 的尺度会随分布集中而收紧**——
字体变好 → 分布变集中 → MAD 变小 → 同样 6 倍标准差对应的**绝对**偏差门槛跟着收紧 →
离群数**不降反升**。实测：换成逐字选源后，绝对阈值 |差|≥12 的汉字从 204 降到 63，
而 z-score 判据的命中数却从 17 涨到 151 —— 那是**量具在骗人**，不是字体变差。

跨版本比较必须用绝对量，所以固定阈值 12。
12 的来由：被填死的字比参考少 20 多个竖笔分段（量 −28 / 舅 −24 / 暴 −22），
正常字只差 1–3 个；12 落在两者之间。

### 字腔数这个量具本身也验过

`count_holes` 是整条链的地基（路由推导、硬检查、缺陷判定全靠它）。它用**并查集**
写了一份**完全不同的第二实现**做交叉验证：

- 400 个汉字 × 2 个源 = **800 次**比较 → **0 处不一致**
- 参考字体抽样 **2286** 个字形 → **0 处不一致**

> **第一版并查集校验器自己写错了**：它把"同时贴到字形外接矩形边界的白区"也算成了腔，
> 800 次里 667 次不一致。修法是"先标出所有含边界格的根，再把这些根整体排除"。
> **量具自己也会撒谎** —— 交叉验证必须用真正不同的代码路径，
> 而且校验器写错时的表现和被测对象错时**一模一样**。

字腔定义（写在这里，避免各工具实现漂移）：
**4 邻域**下被墨迹完全包围的白区连通分量数，按墨迹**外接矩形**计；
任何碰到外接矩形上下左右任一边界的白区**不算腔**（那是外部背景）。

## 4. 目视复核

44 张对照图切成 lane 并行复核（每 lane 6 张 = 576 字）：

| lane | 范围 | 复核字数 | 身份错误 | 确认劣化 | 存疑 |
|---|---|---|---|---|---|
| lane1 | sheets 0-5（ASCII + 标点 + 假名 + 汉字前段） | 576 | **0** | 5 | 11 |
| lane2 | sheets 6-11 | 576 | **0** | 3 | 3 |
| lane3 | sheets 12-17 | 576 | **0** | 13 | 16 |
| lane4 | sheets 18-23 | 576 | **0** | 8 | 11 |
| **合计** | | **2304** | **0** | **29** | **41** |

**2304 字，0 个身份错误。** 即：没有空白格、没有豆腐块、没有两个码位画成同一个字。

各 lane **独立地**都拿"封闭字腔数"当结构指标（lane1 原话：*"封闭字腔数与最大实心矩形面积
曾用于排序候选，但会被分辨率差严重干扰……故只作候选提示，最终判定一律以目视为准"*），
与自动化判据的结论完全吻合。

lane3 自己发现了对照图生成器的一个缺陷并如实记录：*Unifont 16px×3=48px 超出 42px 槽位，
前格 Unifont 墨迹串到下一格「我方」列左缘 1–2 个源像素（111 格）*。
该污染只落在背景像素上（我方列是后贴的，会覆盖参考墨迹），
**lane3 的判定一律以 PNG 原图为准**，未受污染影响。

## 5. 发现的异常与处理

### 5.1 身份错误：0 例

**没有任何一个码位画成了错误的字。** 这是本轮校验最重要的结论。

### 5.2 逐像素撞车 5 例 —— 全部是合法同形字

| 我方 | 与之逐像素相同 |
|---|---|
| `゙` U+3099 | `〪` U+302A |
| `゜` U+309C | `〪` U+302A |
| `。` U+3002 | `〭` U+302D |
| `－` U+FF0D | `ߺ` U+07FA |
| `＝` U+FF1D | `̳` U+0333 / `‗` U+2017 |

这些是 Unicode 里的**同形异义码位**（组合记号之间、带圈点与句点的不同码位），
在 12px 点阵下画出来必然一样。**不是缺陷**，仅记录。

### 5.3 结构塌陷：根因与修法

根因：源字体 SimHei 是**平滑轮廓字体**，12px 下密笔画汉字的部件横画会粘连，
把「日」「目」「田」这类部件的字腔整个填死 —— 整字渲染成一块白块。

以「量」为例（12×12 外接框）：

```
我方 (SimHei MONO)          Ark Pixel 12px
.########.                 .#########..
.########.                 .#.......#..
.########.                 .#########..
##########                 .#.......#..
.########.                 ###########.
.########.                 .#...#...#..
.#..#...#.                 .#########..
..######..                 .#...#...#..
.########.                 .#########..
##########                 .....#......
                           ###########.
```

上半部「日」整个被填实。我方 10×7 全部是实心墨。

**为什么不是换二值化阈值就能解决**：实测了 5 种栅格化策略（FreeType MONO、
灰度 128/144/160/176），以"字腔数均值"打分：

| 策略 | 字腔均值 | 参考 | dcol 中位 | dcol ≤ −18 的字 |
|---|---|---|---|---|
| **MONO（当前）** | **2.30** | 2.39 | **−4.0** | **24** |
| 灰度 128 | 1.16 | 2.39 | −6.0 | 113 |
| 灰度 144 | 0.61 | 2.39 | −8.0 | 202 |
| 灰度 160 | 0.25 | 2.39 | −10.0 | 440 |
| 灰度 176 | 0.08 | 2.39 | −13.0 | 916 |

**MONO 反而是最好的**（FreeType 的 hinting 把笔画吸附到像素格，保住了 1px 粗细）。
而且 SimHei 的「日」在 12px 只有 4 行 —— 3 横 2 腔根本放不下，
**这是源字体在该尺寸的固有极限，不是阈值问题**。

**修法**：MS Gothic 的 12px 是**原生点阵位图**（80 年代手工点的），字腔是活的；
项目本来就在用它出假名与拉丁。问题只在**哪些字该换源**。

### 5.4 选源规则：从"只切白块"到"逐字选源"

最初的判据是"SimHei 渲染出 0 腔 → 切到 MS Gothic"（下称 blob 模式），
只能覆盖**整字**塌陷。但目视复核认定的问题**多数是局部塌陷**
（某个部件被填死，整字还有腔）—— blob 模式一个都抓不到。

改成**逐字选源**：对每个汉字，比较 SimHei 与 MS Gothic 的**结构签名**
（字腔数 / 竖笔画分段数 / 横笔画分段数）离参考字体的距离，取更近者。

距离函数：

```
距离 = w×|字腔差| + |竖笔差| + |横笔差|
```

**w 的取值是标定出来的**，不是拍的。理由：字腔是**拓扑量**，不受字宽与分辨率影响；
横/竖笔画分段数则对参考字体的分辨率与字宽天然有偏（参考 12px 宽的字，
同一行里能放下更多墨段，横笔差天然偏大）。

| w | 切换数 | 确认劣化覆盖 | 存疑覆盖 | 字腔达标 | 竖笔达标 | 横笔达标 | 腔差均值 |
|---|---|---|---|---|---|---|---|
| 1 | 2032 | 20/21 | 18/30 | 83.8% | 38.7% | 52.8% | 0.703 |
| **4** | **1952** | **20/21** | **19/30** | **86.4%** | 37.6% | 51.3% | **0.623** |
| 12 | 1859 | 18/21 | 17/30 | 87.6% | 36.4% | 49.8% | — |
| 纯字腔优先 | 1857 | **18/21** | 17/30 | 87.6% | 36.3% | 49.7% | 0.586 |

选 **w = 4**：字腔达标率与腔差均值明显改善，确认劣化仍 20/21，存疑覆盖最高。
纯字腔优先（字腔差不等就只看字腔）**反而丢 2 个确认劣化字**
（羹 U+7FB9、霍 U+970D）—— 它们的字腔数本来就对，塌的是**笔画**，
所以笔画分段数必须留在判据里，不能让字腔一票否决。

#### 字腔硬约束

再加一条**硬约束**：参考字体说这个字该有腔，而某个候选源渲染出 **0 腔**
（整字白块），另一个候选源有腔 —— 那就**必须**选有腔的那个，不看笔画数差多少。

理由：0 腔是**可见的硬错误**（整个字渲染成一块白块），笔画数差只是风格差异。

实测这条约束修掉了 blob 模式下漏掉的「粔」U+7CD5：
不加约束时它被判给 SimHei（0 腔，白块），加了之后改判 MS Gothic（3 腔）。

#### 最终路由名单

| 项 | 数值 |
|---|---|
| 模式 | `per_char`（逐字选源） |
| 字腔权重 | 4 |
| 切到 MS Gothic | **1930** 个码位 |
| 保持 SimHei | 1825 个 |
| 与参考的结构距离均值 | 11.28 → **7.43** |
| 与参考完全吻合的汉字 | 21 → **168** |

名单存在 `tools/fontgen/ideo_route.json`，
由 `tools/fontgen/derive_ideo_route.py --per-char --hole-weight 4` 重新推导，
**不靠人肉维护一张表**。

#### 修法里的一个坑

推导脚本第一版按"渲染结果有没有腔"判断备选源行不行，结果推出 95 个码位 ——
其中 39 个是 **MS Gothic 根本没有的字**。原因：FreeType 对缺字会画 `.notdef`
—— 一个**空心矩形**的豆腐块，它自带 1 个"字腔"。
改成查 cmap 覆盖后，正确结果是 56 个。**这个坑是构建门禁当场抓出来的**（见 5.7）。

### 5.5 局部塌陷：目视抓得到，自动抓不到

目视复核找出 29 例**确认**的结构劣化和 41 例存疑。
这些是**部件级**的粘连：整字还有腔，但某个部件（日 / 雨 / 田 / 革）被填死。

### 5.6 检测极限：自动判据的召回率是 5/29

用 4 条 lane 的目视标记当标定集，反查自动判据（`tools/fontgen/calibrate_detector.py`）：

| 指标 | 结果 |
|---|---|
| 确认 DEGRADED 召回 | **5 / 29** |
| 存疑召回 | **4 / 41** |
| 判据 `EXACT_COLLIDE` | 可靠 |
| 判据 `COUNTER_LOST` | 只对"整字塌陷"可靠 |

**为什么抓不到**：标定集里有两个反例 ——

- **瓣**（U+74E3）：我方字腔 **7** 个，参考 **5** 个 —— 我方**还多**；
- **雹**（U+96F9）：我方字腔 **6** 个，参考 **2** 个 —— 我方**还多**。

两个都被目视判为 DEGRADED。塌陷发生在**某一个部件**里，全字腔数完全看不出来。
所有基于腔数/方块面积的阈值都无法区分它们：

| 判据 | 命中总数 | 标定集命中 | 误报率 |
|---|---|---|---|
| 腔数差 ≥ 2 | 501 | 17/70 | 96.6% |
| 腔数差 ≥ 3 | 240 | 14/70 | 94.2% |
| 腔数比 < 0.6 | 521 | 15/70 | 97.1% |
| 最大实心方块比 ≥ 1.5 | 2082 | 21/70 | 99.0% |

**所以正确的分工是：自动判据筛高危，目视复核做最终判定。**
报告里必须写明这个检测极限，不能让人误以为自动检查已经覆盖了全部缺陷。

> 注意这个召回率数字的**读法**：标定集是**修复前**的对照图上标的字。
> 修复之后，大部分劣化字已经好了，自动判据自然不再报它们 → 召回率看起来"变差"。
> 跨版本比较必须看**修复前后的命中总数**（818 → 340 → **93**），
> 不能拿修复后的召回率去说"检测能力退步了"。

### 5.7 构建门禁

`charset.gate_ideo_route()` 在每次构建时逐个核对名单里的字**仍然**满足切源理由：

- **签名比对**：重算 SimHei / MS Gothic 的结构签名，与名单里记录的不一致就说明
  源字体版本变了 → 切源依据已过期，拒绝构建；
- **切源理由复核**：用名单里记录的参考签名**复算距离比较**，
  确认"切过去确实更好"依然成立（或字腔硬约束依然成立）；
- 名单条目缺签名 / 非汉字源已不含该字形 → 拒绝构建。

名单是按"当前这两个源字体"推导的。换了 SimHei / MS Gothic 版本，某个字可能不再塌陷，
那时切过去反而会引入不必要的风格差异。这种事不能靠人记得回头看一眼，所以硬拦。

**门禁做过自检**（注入必须真的落地）：

```
注入: 把 U+4E01 名单条目的 sig_ideo[0] 从 3 改成 0 (伪造源字体版本变化)
结果: 构建被拒 (exit 1)
      "ideo 路由名单失效, 共 1 个码位:
         U+4E01 '丅' 结构签名与推导时不一致 (记录 ideo=[3,11,10]/alt=[0,12,10],
         现 ideo=[0,11,10]/alt=[0,12,10]) —— 源字体版本变了, 请重新推导名单"
恢复: 构建通过 (exit 0)
```

### 5.8 仍未修复的 20 个白块：两个源都画不出来

路由覆盖了目视标记的 **52 / 70** 个（29 个确认劣化里 25 个、41 个存疑里 27 个）。
剩下 18 个未被路由覆盖，其中 **4 个是目视确认的劣化**：

| 码位 | 字 | MS Gothic | Ark Pixel | Zpix | 硬检查怎么说 |
|---|---|---|---|---|---|
| U+568E | 嚎 | **无此字** | 有 | 有 | `STRUCTURE_OUTLIER`（竖笔画比参考少 12） |
| U+9611 | 迸 | **无此字** | 有 | 有 | 硬检查未命中（局部塌陷，自动判据无能为力） |
| U+9C81 | 鬣 | **无此字** | 有 | 有 | `STRUCTURE_OUTLIER`（竖笔画比参考少 16） |
| U+9CDE | 鲨 | **无此字** | 有 | 有 | 硬检查未命中（局部塌陷） |

这 4 个的共同点：**MS Gothic 根本没有这些汉字**，只能靠 SimHei 的平滑轮廓，
而 SimHei 在 12px 下把它们画塌了。

同样地，**24 条 `COUNTER_LOST` 里有 20 个汉字**属于这一类 ——
它们在当前字体里**渲染成整块白块**，是用户能直接看见的缺陷。

另有 4 条 `COUNTER_LOST` 是**假名**（`゙` U+309A / `タ` U+30BF / `ダ` U+30C0 / `ﾀ` U+FF80）：
这些字由 MS Gothic 出，MS Gothic 自己就没画出封闭空间，Ark 画出了。
这是**画风差异**（PC-98 点阵的 タ 就是没有封闭腔），不是身份错误。

## 6. 尚未采纳的方案：引入第三个像素源

既然根因是"**两个生产源都不行**"，最直接的解法是**把开源像素字体也当生产源**。
Ark Pixel 12px（OFL-1.1）本来就是本项目的参考字体之一，
它覆盖我们 3755 个汉字里的 **3605** 个。

按同一条 w=4 + 字腔硬约束规则做**多源**逐字选源（严格查 cmap，不让 `.notdef` 混入）：

| 方案 | 各源胜出 | 与参考结构距离均值 | 完全吻合 | 确认劣化覆盖 | 存疑覆盖 | **剩余白块** |
|---|---|---|---|---|---|---|
| **A. 双源**（SimHei + MS Gothic，当前） | msgothic 1930 / simhei 1825 | 7.43 | 168 | 20/21 | 19/30 | **20** |
| **B. 三源**（+ Ark Pixel） | ark 3440 / msgothic 230 / simhei 85 | **0.38** | **3608** | **21/21** | **28/30** | **0** |

B 方案把"与参考的结构距离"降了 20 倍，把完全吻合的汉字从 168 个提到 3608 个，
**剩余白块归零**。嚎 / 迸 / 鬣 / 鲨 这 4 个在 B 下全部改用 Ark Pixel，
嚎的结构距离从 38 降到 **0**（Ark 的签名与参考完全一致）。

**代价**（必须说清，不能只报好处）：

1. **来源与许可证**：Ark Pixel 是 OFL-1.1，需要入库（裁剪到本项目字符集后约 730 KB）
   并附许可证；字体的字形来源从"SimHei 轮廓栅格化 + MS Gothic 点阵"变成三源混排。
2. **画风一致性**：Ark 的汉字在 12px 网格里占 12 行、SimHei 占 10 行、
   MS Gothic 占 11 行 —— 三种字高混排在一起，肉眼可见大小不一致。
   （注意：当前的双源方案**已经**存在 10 行 vs 11 行的混排。）
3. **em-box 约定不同**：Ark 的 ascent 是 10、SimHei / MS Gothic 是 11，
   直接混用会**错基线 1px**，必须做基线归一化。
4. Ark 的 zh_hans 变体**缺 150 个汉字**，这 150 个无论如何都得留在 SimHei。

**中间方案 C**：保留双源逐字选源，只把**当前渲染成白块的 20 个汉字**交给 Ark Pixel。
风格影响最小，白块也归零，但嚎 / 迸 / 鬣 / 鲨 这类"部分塌陷"仍不修。

> 该方案的取舍属于**方向选择**（字体来源与画风），需要拍板后再落地。

## 7. 复现步骤

```bash
# 1. 取参考字体 (开源免费, 不入库, 只记来源与 sha256)
python tools/fontgen/fetch_ref_fonts.py
python tools/fontgen/fetch_ref_fonts.py --verify

# 2. 自动化硬检查 (注意 --json 才是 JSON 输出路径, --out 是 markdown 路径)
python tools/fontgen/compare_refs.py --screen-only \
    --refs ark-pixel-zh_hans,fusion-pixel-zh_hans,zpix,unifont-16 \
    --json reports/glyphcmp_screen.json

# 3. 生成对照图
python tools/fontgen/gen_glyphcmp_sheets.py \
    --refs fusion-pixel-zh_hans,unifont-16 \
    --cols 12 --rows 8 --scale 2 \
    --outdir reports/glyphcmp_png --index reports/glyphcmp_index.json

# 4. 量具自检: 自动判据对着目视标定集的召回率
python tools/fontgen/calibrate_detector.py \
    --screen reports/glyphcmp_screen.json --review reports/glyphcmp_review \
    --out reports/glyphcmp_calibration.json

# 5. 汇总各 lane 的目视复核 + 与路由名单对账
python tools/fontgen/aggregate_glyphcmp_review.py \
    --out reports/glyphcmp_review/summary.json \
    --md  reports/glyphcmp_review/summary.md
python tools/fontgen/account_fixes.py

# 6. 重新推导路由名单 (换源字体版本后必须跑)
python tools/fontgen/derive_ideo_route.py --per-char --hole-weight 4

# 7. 构建 + 全量回归
python tools/fontgen/build_font.py
python tools/fontgen/regress_all.py
```

## 8. 已知限制

1. **20 个汉字仍然渲染成白块**：MS Gothic 没有这些字，SimHei 在 12px 画不出来。
   根治要么引入第三个像素源（见第 6 节），要么换更大网格。
2. **局部塌陷**（约 14 例）目前只能靠目视发现，自动判据无能为力（见 5.6）。
3. **参考集只有 3 票**（Ark / Zpix / Unifont）。Cubic 11 的 4 个候选 URL 全部 404，
   Fusion 虽是缝合产物但其实测与 Ark 结论一致。独立票数不足是本方法最根本的限制。
4. Ark 缺 150 个汉字、Zpix 缺 12 个假名，这些码位在对应参考下**无法比对**，
   只能靠另两套参考 + 目视。
5. **目视复核只覆盖了 2304 / 4140 字**（sheets 0-23），后 20 张图（1836 字）
   目前只有自动化硬检查覆盖。
6. 对照图生成器有个已知缺陷：Unifont 16px×3=48px 超出 42px 槽位，
   前格 Unifont 墨迹会串到下一格「我方」列左缘（111 格污染背景像素）。
   lane3 的判定以 PNG 原图为准，未受影响；生成器尚未修。
