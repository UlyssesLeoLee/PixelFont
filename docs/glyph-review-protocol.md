# 字形目视复核协议

本文件是 8 条复核 lane 的**统一作业协议**。每条 lane 读这份文件再开工,
不要各自发挥 —— 上几轮不同 lane 的判定口径不一致, 汇总时才发现要额外归一化。

## 1. 任务

对分配到的每一张对照图, **逐格**回答一个问题:

> **我方那一列, 画的是不是标注的那个字? 笔画结构有没有塌?**

参考列给出"同一个字在别的像素字体里长什么样", 用来判断我方的结构有没有丢。

## 2. 输入

| 文件 | 说明 |
|---|---|
| `reports/glyphcmp_png/glyphcmp_NNN.png` | 对照图, 12 列 × 8 行 = 96 格 |
| `reports/glyphcmp_index.json` | **格位映射的权威**: `sheets[i].chars` 是该图第 i 格的码位序列 (格序 = 从上到下、每行从左到右) |
| `reports/glyphcmp_review/laneN.json` | 你的产物 (结构见第 6 节) |
| `reports/glyphcmp_review/laneN.md` | 你的产物 (给人看的报告) |

**格位映射必须以 index JSON 为准**, 不要靠图上的低分辨率标签条带目视读码位。

## 3. 格子几何

| 项 | 值 |
|---|---|
| 槽位 | 16×16 源像素, 放大 2 倍 → 32×32 屏幕像素 |
| 格宽 / 格高 | 108 / 66 屏幕像素 |
| 表头高 | 26 像素 |
| 第 r 行第 c 列的格子左上角 | `x = c*108`, `y = 26 + r*66` |
| 格内标注 (标准答案字形 + 码位) | `y+3` 与 `y+9` 处, 微软雅黑渲染 |
| 三列点阵的左上角 | 我方 `x+2`、Zpix `x+38`、Unifont `x+74`; 纵坐标都是 `y+30` |

> **槽位是 16×16 不是 12×13**: Unifont 是 16px 字体。早期的出图工具把槽位固定成
> 12px, 导致 Unifont 那一列的墨迹**溢出到下一格「我方」列的左缘** (实测污染 111 格),
> 复核者看到的不再是干净的对照。已修: 槽位按所有列的最大字形算, 并且每列都裁剪到自己的槽位。

## 4. 参考列为什么是 Zpix + Unifont

**不是** Ark Pixel 和 Fusion Pixel —— 原因是实测出来的, 不是偏好:

- Ark Pixel 现在是**生产源** (1043 个汉字直接用它的原生点阵), 拿它当参考等于自己和自己比。
- Fusion Pixel 的简体版与 Ark Pixel 的结构距离实测 **0.00** (3605 个汉字全部完全一致),
  也就是 Fusion zh_hans 就是 Ark zh_hans —— 它**不提供任何独立票**。

真正独立的是 **Zpix** (MIT, 与 Ark 无亲缘) 与 **GNU Unifont** (GPL-2.0+, 16px, 学术级点阵)。

代价: Zpix 的画风比 Ark/Fusion 粗犷, 与我方的**像素级**差异更大
(实测我方 vs Zpix 完全吻合的汉字只有 225 个, vs Fusion 是 1212 个)。
所以判定原则要相应调整, 见下节。

## 5. 判定口径

### A 类 = IDENTITY (画的不是这个字)

我方那一列画出来的字形与标注字**明显不是同一个字**。
这是最严重的一类, 也是本轮校验最关心的结论。

### B 类 = DEGRADED (是此字, 但笔画粘连 / 结构丢失, 明显差于两个参考)

判定**按骨架, 不按像素**:

- 某个部件 (日 / 目 / 田 / 革 / 雨 / 木 …) 的封闭空间被填实 → B
- 部件的横画消失、竖画并成一条实心带 → B
- 整字只剩一两个封闭腔, 而两个参考都明显分得出多个结构 → B
- 轮廓仍可辨、只是笔画比参考粗/密 → **不是 B**, 归 C (存疑) 或不报

Zpix 比 Ark 粗犷, 像素级差异不算劣化。**只有"结构信息丢失"才算 B。**

### C 类 = 存疑 (不判定)

处在 B 的门槛上: 笔画明显比参考密, 但结构仍可追踪, 两个参考之间自己也不一致。
**如实记下来, 不要为了好看而往 B 上靠。**

### 辅助量化: 字腔数

字腔 = 被墨迹完全包围的白区连通分量数, **4 邻域**, 按墨迹外接矩形计;
**碰到外接矩形上下左右任一边界的白区不算腔** (那是外部背景)。

字腔是**拓扑量**, 不受字宽与分辨率影响, 是唯一被实测证明有分辨力的结构指标 ——
3 套独立参考一致认定的"零腔"字, 目视确认**全部**是白块。

**但你自己算的字腔数必须先自检**: 写两份**不同实现**的腔数统计
(例如洪水填充 + 并查集), 对全量字形跑一遍, 两者不一致就说明你的实现有问题。
上一轮真踩过: 一份实现把"贴边区域"算成了腔, 800 次比较里 667 次不一致,
而它错的时候表现和正确时**一模一样**。

## 6. 产物格式

### `reports/glyphcmp_review/laneN.json`

```json
{
  "lane": 1,
  "sheets": [{"sheet": "glyphcmp_000.png", "chars": 96, "first": "U+0020", "last": "U+007F"}],
  "chars_reviewed": 480,
  "findings": [
    {"cp": "U+91CF", "char": "量", "kind": "B",
     "reason": "顶部「日」填实成实心白块, Fusion 能分出两腔, Unifont 更清晰 (腔 2 vs 6)",
     "confidence": "medium"}
  ],
  "unsure": [
    {"cp": "U+554A", "char": "啊", "kind": "C",
     "reason": "最左「口」塌成 2px 实心竖条, 但右部「阿」仍可辨, 属局部塌陷",
     "confidence": "low"}
  ],
  "summary": {"identity": 0, "degraded": 12, "chars_reviewed": 480},
  "method": {"artifact": "...", "refs": ["Zpix 12px (MIT)", "GNU Unifont 16x16 (GPL-2.0+)"],
             "basis": "全部判定以出图 PNG 原图为唯一底本", "steps": ["..."]}
}
```

字段说明:

- `findings` = A 类 + B 类 (身份错误与确认劣化)
- `unsure` = C 类
- `cp` 必须是 `"U+XXXX"` 大写十六进制字符串
- `chars_reviewed` = 你**逐格看过**的字数, 不是"覆盖到的字数"

### `reports/glyphcmp_review/laneN.md`

给人看的报告: 复核范围、结论表 (身份错误 / 确认劣化 / 存疑 各多少)、
异常清单 (码位 / 字符 / 位置 / 类别 / 理由 / 置信度)、存疑清单、方法说明。

## 7. 作业纪律

1. **以 PNG 原图为唯一底本**。不要用低分辨率标签条带判断格位。
2. **放大看**: 用 8x/12x 放大裁切逐格看, 不要只扫缩略图。
3. **每一格都要过**。`chars_reviewed` 必须等于分配给你的格数。
4. **不许改源码**。复核期间 `tools/fontgen/` 下的文件可能被集成者并发修改,
   那不影响你的判定 —— 你的结论以 PNG 原图为准。
5. **发现问题如实记**, 不要为了"看起来干净"而漏报或压低置信度。
6. **量具要自检**: 你的量化工具 (腔数等) 出错时表现和对的时候一模一样,
   交叉验证过再用它的数字。
7. 如果你发现自己早先的结论与最终产物不一致, **在报告里写明改前值**, 不要静默改数。

## 8. 已知问题 (不用你管, 但要知道)

- 我方字体是 12×13 网格, 参考里 Unifont 是 16×16 —— 纵向不可直接比像素, 只比骨架。
- MS Gothic 的假名 (タ/ダ/ﾀ) 在 PC-98 点阵里本来就没有封闭腔, 与 Unifont/Zpix 不同,
  这属于**画风差异**不是缺陷, 不要报 B。
- Ark Pixel 缺本项目 150 个汉字, Zpix 缺 12 个假名 —— 缺格显示"缺", 跳过即可。
